Refs & the DOM with useRef

⚛️ React ⏱️ ~24 min 📌 Escape hatch

Sometimes you need a value that persists across renders but doesn't trigger a re-render, or you need direct access to a real DOM element. useRef is the hook for both. It's an escape hatch from React's declarative model — used sparingly, but essential for focus management, measuring elements, and storing mutable values like timers.

1. Refs to DOM elements

FocusInput.tsxtsx 
import { useRef } from "react";

function SearchBar() {
  // Typed ref to an input element, initially null:
  const inputRef = useRef<HTMLInputElement>(null);

  const focusInput = () => {
    inputRef.current?.focus();   // .current is the actual DOM node (or null)
  };

  return (
    <div>
      <input ref={inputRef} placeholder="Search..." />
      <button onClick={focusInput}>Focus the input</button>
    </div>
  );
}
Attach a ref via the ref attribute, then read the DOM node from ref.current. Type it with the element type (HTMLInputElement); it starts null and React fills it in after mount — hence the ?.. Use this for focus, scrolling, measuring, and integrating non-React libraries (charts, maps).

2. Refs as mutable instance values

Stopwatch.tsxtsx 
import { useRef, useState } from "react";

function Stopwatch() {
  const [seconds, setSeconds] = useState(0);
  const intervalRef = useRef<number | null>(null); // survives renders, no re-render

  const start = () => {
    if (intervalRef.current !== null) return;
    intervalRef.current = window.setInterval(() => setSeconds((s) => s + 1), 1000);
  };
  const stop = () => {
    if (intervalRef.current !== null) {
      clearInterval(intervalRef.current);
      intervalRef.current = null;
    }
  };

  return (
    <div>
      <p>{seconds}s</p>
      <button onClick={start}>Start</button>
      <button onClick={stop}>Stop</button>
    </div>
  );
}
A ref is a box whose .current you can mutate freely — and changing it does not trigger a re-render. That's exactly what you want for a timer ID: it must persist across renders, but updating it shouldn't redraw the UI. Contrast with state, where every change re-renders.

3. State vs Ref — the decision

⚠️
Gotcha · Don't read/write refs during render

Reading or mutating ref.current during rendering is unsafe (it breaks React's purity assumptions). Touch refs in event handlers and effects — after render. If a value affects what's displayed, it belongs in state, not a ref.

✨
React 19 · ref as a prop

In React 19 you can pass ref to a function component as a normal prop — no more forwardRef wrapper. function Input({ ref }: { ref: Ref<HTMLInputElement> }) just works. This simplifies building reusable input components for design systems (Part 8).

Exercise · Track the previous value

Build a counter that also shows its previous value. Use a ref updated inside a useEffect to remember the last count. Observe that the ref lets you keep history without causing extra renders — a classic ref use case.

🎓 Key takeaways

  • useRef holds a mutable .current that persists across renders without causing re-renders.
  • Attach ref to an element to access the real DOM node (focus, scroll, measure, 3rd-party libs).
  • Use refs for non-visual mutables: timer IDs, previous values, instance flags.
  • If a value affects the UI, use state; if it's behind-the-scenes, use a ref.
  • React 19 lets you pass ref as a regular prop — no forwardRef.
