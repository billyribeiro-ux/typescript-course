Side Effects with useEffect

⚛️ React · nuanced ⏱️ ~34 min 🔌 Syncing with the outside

Components are pure functions of state — but real apps must talk to the outside world: timers, subscriptions, the DOM, and (historically) data fetching. useEffect is the escape hatch for these side effects. It's also the most misused hook in React, so we'll teach it carefully: when to use it, the dependency array, cleanup, and — importantly — when not to use it.

1. The shape of an effect

effect-basics.tsxtsx 
import { useState, useEffect } from "react";

function Title({ count }: { count: number }) {
  useEffect(() => {
    // This runs AFTER render, as a side effect:
    document.title = `Count: ${count}`;
  }, [count]); // ← the DEPENDENCY ARRAY: re-run only when `count` changes

  return <p>Check the tab title.</p>;
}

// The dependency array controls WHEN the effect runs:
//   [count]  → after renders where count changed
//   []       → once, after the first render (on "mount")
//   (omitted) → after EVERY render (rarely what you want)
The dependency array is everything. React re-runs the effect only when a listed dependency changes. [] means "run once on mount". Omitting it means "run after every render" (usually a bug). The ESLint exhaustive-deps rule (lesson 03-04) checks that you list every value the effect uses — trust it.

2. Cleanup — the return function

cleanup.tsxtsx 
function Clock() {
  const [time, setTime] = useState(() => new Date());

  useEffect(() => {
    const id = setInterval(() => setTime(new Date()), 1000); // subscribe

    // The returned function is CLEANUP — runs before re-run and on unmount:
    return () => clearInterval(id);   // unsubscribe → no memory leak
  }, []); // set up once

  return <p>{time.toLocaleTimeString()}</p>;
}
If an effect sets something up, it must tear it down. The function you return from the effect is the cleanup — React runs it before the next effect run and when the component unmounts. Timers, event listeners, and subscriptions all need cleanup or they leak. Set up / tear down is the mental model: the effect describes a synchronization, not a one-time action.

3. Data fetching (and the modern caveat)

fetch-in-effect.tsxtsx 
function UserCard({ id }: { id: number }) {
  const [user, setUser] = useState<User | null>(null);

  useEffect(() => {
    let cancelled = false;                 // guard against race conditions
    fetch(`/api/users/${id}`)
      .then((r) => r.json())
      .then((data) => { if (!cancelled) setUser(data); });
    return () => { cancelled = true; };     // ignore stale responses
  }, [id]);

  if (!user) return <p>Loading...</p>;
  return <p>{user.name}</p>;
}
interface User { name: string }
You can fetch in an effect, but in 2026 you usually shouldn't. The cancelled flag prevents a slow earlier request from overwriting a newer one (a real race bug). But manual fetching means handling loading, errors, caching, and races yourself — which is exactly what TanStack Query (Part 6) does for you. Learn this to understand the problem; use the library to solve it.

4. When NOT to use useEffect

⚠️
Gotcha · The most over-used hook

You do not need an effect to: transform data for rendering (just compute it during render), respond to a user event (do it in the handler), or reset state when a prop changes (use a key instead). Effects are for synchronizing with external systems — the DOM, network, timers, subscriptions. If no external system is involved, you probably don't need an effect.

no-effect-needed.tsxtsx 
// ❌ Unnecessary effect + extra state:
const [fullName, setFullName] = useState("");
useEffect(() => { setFullName(`${first} ${last}`); }, [first, last]);

// ✅ Just compute it during render — it's derived data:
const fullName = `${first} ${last}`;
Derived values are computed during render, not stored in state + an effect. This is the #1 React anti-pattern. If a value can be calculated from props/state, calculate it inline. Reserve useEffect for genuine external synchronization.
✨
2026 context · Effects are shrinking

Modern React deliberately reduces effect usage: data fetching → TanStack Query or Server Components (Part 7); form state → React Hook Form; derived state → compute inline. You'll write far fewer effects than old tutorials suggest — and the ones you do write will be cleaner for it.

Exercise · Effects with cleanup

1) Build a component that adds a window "resize" listener in an effect and displays the current width, cleaning up on unmount. 2) Then find a piece of "derived state + effect" in your own code (or write one) and refactor it to a plain computed value during render.

🎓 Key takeaways

  • useEffect runs side effects after render; the dependency array controls when ([] = once).
  • If an effect sets something up, return a cleanup function (timers, listeners, subscriptions).
  • Fetching in effects needs a race guard; prefer TanStack Query (Part 6) in real apps.
  • Don't use effects for derived data, event responses, or prop-driven resets.
  • Effects are for syncing with external systems — and you'll write fewer than you think.
