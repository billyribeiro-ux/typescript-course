Part 4 · React Core — Lesson 1

Thinking in React & the Component Model

⚛️ React ⏱️ ~26 min 🧠 The mental model

You've mastered TypeScript and tooling. Now we build user interfaces with React — the library behind most of the modern web. Before any syntax, you need React's core mental model, because it's a genuine shift from the DOM manipulation you saw in Part 0. Get this model right and everything else clicks; get it wrong and you'll fight the framework forever.

1. The big idea: UI as a function of state

In Part 0 you changed the page imperatively: "find this element, set its text". React is declarative: you write a function that returns what the UI should look like for the current data, and React figures out the DOM changes. The mental formula:

🧩
Concept · UI = f(state)

Your interface is a function of state. Given the same data, a component always renders the same output. When the data changes, React re-runs your function and efficiently updates only the DOM that actually changed. You describe the destination; React handles the journey.

2. Components: the building blocks

A component is a function that returns UI (written in JSX, next lesson). Components are composable — you build complex screens by nesting small, focused components, just like composing functions. This is the same "break big problems into small ones" principle from lesson 00-01, applied to interfaces.

Welcome.tsxtsx 
// A component is just a function that returns UI.
function Welcome() {
  return <h1>Hello, React!</h1>;
}

// Components compose — build big UIs from small pieces:
function Avatar() {
  return <img src="/me.png" alt="Me" width={48} />;
}

function Header() {
  return (
    <header>
      <Avatar />        {/* use a component like an HTML tag */}
      <Welcome />
    </header>
  );
}

// Rule: component names MUST start with a capital letter.
// <Avatar /> is a component; <avatar /> would be treated as an HTML tag.
Components are functions that return UI. You use them like custom HTML tags (<Avatar />). The capital-letter rule is how React (and the compiler) tells your components apart from built-in HTML elements. This composition — small components assembled into bigger ones — is the entire architecture of a React app.

3. The two inputs: props and state

Components have exactly two kinds of data, and the distinction is fundamental:

PropsState
WhatData passed IN from a parentData a component OWNS and can change
Mutable?Read-only (never modify props)Changed via a setter (triggers re-render)
AnalogyFunction argumentsA variable that persists between renders
We cover props in lesson 04-03 and state in 04-04. For now: props flow down from parent to child (one-way data flow), and state lives inside a component. When state changes, React re-renders that component and its children.

4. Why React, concretely

  • Declarative: describe the result, not the steps — far fewer bugs than manual DOM updates.
  • Component reuse: write a Button once, use it everywhere, consistently.
  • The Virtual DOM: React computes the minimal set of real DOM changes, so updates are fast (more in Part 5).
  • Ecosystem: routing, data fetching, forms, animation — a mature library for everything (Part 6).
  • Jobs: React is the dominant UI library at Meta, and used widely across the industry.

Exercise · Decompose a UI

Look at any app you use (say, a Twitter/X feed). On paper, draw boxes around the components you'd create: App → Feed → Tweet → Avatar, TweetActions, etc. For each, note what props it would receive and what state it might own. This decomposition skill is half of React.

🎓 Key takeaways

  • React is declarative: UI = f(state). You describe the result; React updates the DOM.
  • Components are functions returning UI, composed like custom HTML tags (capitalised names).
  • Props flow down (read-only inputs); state is owned and mutable (triggers re-render).
  • React's strengths: declarativeness, reuse, the Virtual DOM, a vast ecosystem, and jobs.
  • We teach React 19 + the React Compiler — the modern 2026 way.
