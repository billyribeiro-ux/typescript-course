useReducer & useContext

⚛️ React + TS ⏱️ ~32 min 🗃️ Structured state

Two hooks for more complex apps. useReducer manages state with the discriminated-union action pattern you mastered in lesson 02-07 — ideal when state transitions get intricate. useContext shares data across the component tree without "prop drilling". Together they form React's built-in answer to app-wide state, and the conceptual basis for Redux (Part 6).

1. useReducer: state transitions as data

useReducer.tsxtsx 
import { useReducer } from "react";

interface State { count: number; step: number; }

// A discriminated union of actions (lesson 02-07!):
type Action =
  | { type: "increment" }
  | { type: "decrement" }
  | { type: "setStep"; step: number }
  | { type: "reset" };

// A pure reducer: (state, action) => newState. Easy to test in isolation.
function reducer(state: State, action: Action): State {
  switch (action.type) {
    case "increment": return { ...state, count: state.count + state.step };
    case "decrement": return { ...state, count: state.count - state.step };
    case "setStep":   return { ...state, step: action.step };
    case "reset":     return { count: 0, step: 1 };
  }
}

function Counter() {
  const [state, dispatch] = useReducer(reducer, { count: 0, step: 1 });
  return (
    <div>
      <p>{state.count} (step {state.step})</p>
      <button onClick={() => dispatch({ type: "increment" })}>+</button>
      <button onClick={() => dispatch({ type: "decrement" })}>-</button>
      <button onClick={() => dispatch({ type: "reset" })}>Reset</button>
    </div>
  );
}
This is lesson 02-07 made interactive. The reducer is a pure function taking the current state and a typed action, returning new state — exactly like the discriminated-union reducers you wrote. You dispatch actions; React runs the reducer and re-renders. Because the reducer is pure, it's trivially unit-testable (just like P01's logic).
⚡
useState or useReducer?

Use useState for simple, independent values. Reach for useReducer when state has multiple sub-values that change together, when the next state depends on complex logic, or when you want transitions described as named actions (great for testing and debugging). The reducer also centralises all the ways state can change in one readable place.

2. The prop-drilling problem

When deeply-nested components need the same data (the current user, the theme), passing it through every intermediate component as props — "prop drilling" — becomes tedious and noisy. Context lets a provider share a value with any descendant directly.

3. useContext

ThemeContext.tsxtsx 
import { createContext, useContext, useState, type ReactNode } from "react";

interface ThemeContextValue { theme: "light" | "dark"; toggle: () => void; }

// 1. Create the context (undefined default forces use within a provider):
const ThemeContext = createContext<ThemeContextValue | undefined>(undefined);

// 2. A provider component owns the state and shares it:
export function ThemeProvider({ children }: { children: ReactNode }) {
  const [theme, setTheme] = useState<"light" | "dark">("light");
  const toggle = () => setTheme((t) => (t === "light" ? "dark" : "light"));
  return <ThemeContext value={{ theme, toggle }}>{children}</ThemeContext>;
}

// 3. A typed custom hook to consume it safely:
export function useTheme() {
  const ctx = useContext(ThemeContext);
  if (!ctx) throw new Error("useTheme must be used within ThemeProvider");
  return ctx;
}

// 4. Any descendant uses it — no prop drilling:
function ThemeButton() {
  const { theme, toggle } = useTheme();
  return <button onClick={toggle}>Theme: {theme}</button>;
}
The professional pattern in four steps: create the context (typed, undefined default), wrap your tree in a provider that owns the state, and expose a custom hook (useTheme) that throws if used outside the provider — so consumers get a guaranteed non-null value with full types. In React 19 you render <ThemeContext> directly as the provider (no .Provider).
⚠️
Gotcha · Context is not a state manager

Context is a transport mechanism, not optimised state management. Every consumer re-renders when the context value changes. It's perfect for low-frequency global data (theme, current user, locale). For high-frequency or large app state, use a dedicated tool — Zustand or Redux Toolkit (Part 6). Combining useReducer + context is a fine middle ground.

🎓 Key takeaways

  • useReducer manages state via a pure (state, action) => state reducer with discriminated-union actions (02-07).
  • Prefer it over useState for complex, multi-field, or transition-heavy state; it's easy to test.
  • useContext shares data across the tree, eliminating prop drilling.
  • Wrap context in a typed custom hook that throws outside its provider for safety.
  • Context is transport, not optimised state — for big/fast state use Zustand/Redux (Part 6).
