Testing, CI/CD & Observability

🎓 Capstone ⏱️ ~45 min ✅ Production-ready

A feature isn't done when it works on your machine — it's done when it's tested, gated by CI, and observable in production. We put ProjectHub on a professional footing with a layered test strategy, a CI pipeline that blocks regressions, and the observability to run it confidently.

1. The testing pyramid, applied

LayerWhat we testHow
StaticTypes, lint, formattsc, ESLint, Prettier (Part 3)
UnitRBAC, billing, board logic, validatorsVitest (P02/P04/P05/P07 style)

Concept · You already wrote most of these

The capstone's pure cores — permissions, billing, board store, validators — are tested exactly like Projects P01–P08 (131 tests across them). Add a handful of API tests (procedures against a test DB) and a few high-value Playwright journeys, and you have confident coverage without testing everything. Test behaviour and contracts, not implementation.

2. The CI pipeline

.github/workflows/ci.ymlyaml 
jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with: { node-version: 24, cache: pnpm }
      - run: pnpm install --frozen-lockfile
      - run: pnpm turbo typecheck lint test build   # all packages, cached (Part 3)
      - run: pnpm turbo test:e2e                      # Playwright on a preview
# Every PR runs this gate; only green code merges. Vercel ships preview deploys
# per PR and auto-deploys main (07-11).
One Turbo command runs the whole gate across the monorepo, cached. typecheck + lint + test + build for every package, then E2E. This is the check script from Part 3 (03-04/09) scaled to a monorepo. A PR that fails any step is blocked; Vercel gives each PR a preview URL to test against (07-11).

3. Production observability

  • Errors: Sentry across client + server, wired into error boundaries (05-04) and tRPC (07-11).
  • Logs: structured, with a per-request trace id (08-06).
  • Vitals & analytics: Core Web Vitals + product analytics, against a performance budget (08-05).
  • Health & alerts: a health endpoint, an SLO, and alerts on user-facing symptoms (08-06).
📝
Exercise · Make a slice production-ready

Take one feature (e.g. "invite member"): write a unit test for the permission/seat logic, an API test for the procedure against a test DB, and a Playwright test for the journey. Wire it into the Turbo CI gate. Add a Sentry breadcrumb and a structured log line. That's the full professional treatment.

🎓 Key takeaways

  • Layer tests: static → unit → integration → API → E2E — most are the pure-core style you've used all course.
  • A single Turbo CI gate (typecheck/lint/test/build + E2E) blocks regressions; previews per PR.
  • Make it observable: Sentry, structured logs with trace ids, vitals + a performance budget, SLOs + alerts.
  • Test behaviour and contracts, not implementation; cover critical journeys, not everything.
  • "Done" means tested, gated, deployable, and observable.
