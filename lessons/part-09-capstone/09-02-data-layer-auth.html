Building the Data Layer & Auth

🎓 Capstone ⏱️ ~50 min 🗄️ Foundation

Every app is built bottom-up from its data. We define ProjectHub's schema with Drizzle (multi-tenant from day one), set up authentication and sessions, and establish the org-scoped access that every query will respect. Get this layer right and the rest of the app rests on solid ground.

1. The multi-tenant schema

packages/db/schema.ts (excerpt)typescript 
import { pgTable, uuid, text, timestamp, integer } from "drizzle-orm/pg-core";

export const orgs = pgTable("orgs", {
  id: uuid("id").primaryKey().defaultRandom(),
  name: text("name").notNull(),
  plan: text("plan").$type<"free" | "pro" | "enterprise">().notNull().default("free"),
});

export const members = pgTable("members", {
  id: uuid("id").primaryKey().defaultRandom(),
  orgId: uuid("org_id").notNull().references(() => orgs.id),
  userId: uuid("user_id").notNull().references(() => users.id),
  role: text("role").$type<"owner" | "admin" | "member" | "viewer">().notNull(),
});

export const projects = pgTable("projects", {
  id: uuid("id").primaryKey().defaultRandom(),
  orgId: uuid("org_id").notNull().references(() => orgs.id), // EVERY row is org-scoped
  name: text("name").notNull(),
});
export type Org = typeof orgs.$inferSelect;
export type Member = typeof members.$inferSelect;
Multi-tenancy means every row belongs to an org. The orgId foreign key on projects (and tasks, etc.) is the tenant boundary — every query must filter by it so org A can never see org B's data. The $type helper makes columns use our string-literal unions (01-03), and types are inferred from the schema (07-06). This is the database backbone.

2. Auth & the request context

packages/api/context.tstypescript 
// Build the per-request context: who is the user, and which org are they acting in?
export async function createContext(): Promise<Context> {
  const session = await auth();                 // Auth.js session (07-08)
  if (!session?.user) return { user: null, member: null };
  // Resolve the user's membership in the active org (role + orgId):
  const member = await db.query.members.findFirst({
    where: (m, { eq }) => eq(m.userId, session.user.id),
  });
  return { user: session.user, member };
}
// tRPC procedures consume this ctx; protectedProcedure requires ctx.member
// (auth + tenancy), and authorize(ctx.member.role, action) enforces RBAC (P07).
The context unifies identity, tenancy, and permissions. Each request resolves the session (07-08) and the user's member record (role + orgId). This is exactly the Context from Project P07's API core — protectedProcedure requires a member, and authorize(role, action) applies the RBAC matrix. Auth, tenancy, and roles, in one place.

3. Org-scoped queries (the safety rule)

⚠️
Gotcha · Every query filters by orgId — no exceptions

The cardinal multi-tenant rule: never query by id alone — always where(eq(projects.orgId, ctx.member.orgId)) too. A single forgotten filter is a data leak across tenants. Centralize this in your data-access functions (a repository layer, 08-01) so it's impossible to forget, and test it (a member of org A must get zero rows from org B).

🎓 Key takeaways

  • Build bottom-up from data: a Drizzle schema where every tenant-owned row has an orgId.
  • The per-request context unifies session (auth), membership (tenancy), and role (RBAC) — P07's model.
  • Every query filters by orgId — centralize it so cross-tenant leaks are impossible.
  • Types flow from the schema (07-06); string-literal unions via $type (01-03).
  • This layer is the foundation everything else composes on.
