Real-Time, Roles & Permissions

🎓 Capstone ⏱️ ~45 min ⚡ Live collaboration

ProjectHub is a collaboration tool, so changes must appear for everyone in real time, and the UI must respect each member's role. We add live updates (so a teammate's task move appears instantly) and wire role-based permissions through both the API and the UI.

1. Real-time updates

realtime.tsxtsx 
"use client";
// When the server pushes a change for this project, invalidate the query so
// TanStack Query refetches — every connected client stays in sync.
function useProjectRealtime(projectId: string) {
  const queryClient = useQueryClient();
  useEffect(() => {
    const es = new EventSource(`/api/projects/${projectId}/stream`); // SSE
    es.onmessage = () =>
      queryClient.invalidateQueries({ queryKey: ["tasks", projectId] });
    return () => es.close();            // cleanup (04-07)
  }, [projectId, queryClient]);
}
// Options: Server-Sent Events (simple, one-way), WebSockets (two-way), or a
// managed service (Pusher/Ably/Supabase Realtime). The mover sees an OPTIMISTIC
// update instantly (06-04); others get it via this push + refetch.
Real-time = a push that invalidates the cache. A teammate's mutation broadcasts an event (via SSE/WebSocket); each client invalidates the affected query (06-04) and refetches, so everyone converges on the same state. The user who made the change sees it instantly via an optimistic update. This is the same caching/invalidation model you already know, plus a push channel.

2. Permissions, end to end

permissions-ui.tsxtsx 
// SERVER (the source of truth): every mutation authorizes (P05/P07):
delete: protectedProcedure.input(z.object({ id: z.string() }))
  .mutation(({ ctx, input }) => {
    authorize(ctx.member.role, "project:edit");   // enforced server-side
    // ...org-scoped delete...
  });

// CLIENT (UX only): hide what the user can't do, using the SAME rules:
const { member } = useSession();
{can(member.role, "project:edit") && <DeleteButton />}
// The UI check is convenience; the SERVER check is security (08-08).
Permissions live in one place and are used twice. The shared can() / authorize() rules (Project P05/P07) enforce security on the server (the real gate) and shape the UI on the client (hiding buttons a viewer can't use). Same source of truth, two purposes — never trust the client for security (08-08).

3. Presence & collaboration polish

  • Presence: show who's online / viewing a project (avatars), via the realtime channel.
  • Optimistic everything: moves, edits, and comments feel instant (04-12 / 06-04), with rollback on failure.
  • Conflict handling: last-write-wins for simple fields; for rich text, a CRDT library (Yjs) — know the trade-offs.
  • Animation: Motion (06-11) for cards entering/leaving and reordering — polish that signals quality.

🎓 Key takeaways

  • Real-time = a server push (SSE/WebSocket) that invalidates the cache so all clients refetch.
  • The mutating user sees an optimistic update; others converge via the push.
  • Permissions use one shared rule set: enforced on the server (security), reflected in the UI (UX).
  • Never trust the client for authorization (08-08) — hide buttons for convenience, gate procedures for safety.
  • Presence, optimistic UI, and animation are the polish that signals a professional product.
