Server Components vs Client Components

🌐 Full-stack · pivotal ⏱️ ~32 min 🔀 The boundary

The single most important concept in modern Next.js: the split between Server Components (the default — render on the server, no interactivity) and Client Components (opt-in with "use client" — run in the browser, can use hooks and events). Getting this boundary right is what separates fast, correct apps from confused ones.

1. The two kinds, side by side

Server Component (default)Client Component ("use client")
RunsOn the server (build/request)In the browser
Can be async / fetch / query DB✅❌ (use hooks/Query)
useState / useEffect / onClick❌✅
Ships JS to the browser❌ (zero)✅
Access secrets / env✅ (safely)❌ (public only)

2. Marking a Client Component

Counter.tsxtsx 
"use client";   // ← this directive opts the file into the client

import { useState } from "react";

export function Counter() {
  const [count, setCount] = useState(0);   // hooks require a Client Component
  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}
"use client" at the top of a file marks it (and its imports) as client code. Anything using useState, useEffect, event handlers, or browser APIs must be a Client Component. Without the directive, you get a Server Component — and using a hook there is a build error that tells you exactly what to do.

3. The pattern: server shells, client islands

app/dashboard/page.tsxtsx 
// Server Component (default): fetches data, renders static shell.
import { Counter } from "./Counter.js";          // a client island
import { db } from "@/lib/db";

export default async function Dashboard() {
  const stats = await db.stats.get();             // server-only data access
  return (
    <main>
      <h1>Revenue: ${stats.revenue}</h1>          {/* server-rendered */}
      <Counter />                                  {/* interactive client island */}
    </main>
  );
}
// You can RENDER a Client Component inside a Server Component freely.
// You can also pass server-fetched data DOWN to clients as props.
The mental model: server shells with client islands. Most of the page is a Server Component (fast, no JS). The interactive bits are small Client Components nested inside. You can render clients within servers and pass data down as props. The boundary is one-directional: a Client Component can't import a Server Component, but it can receive one as children.
⚠️
Gotcha · "use client" is a boundary, not a label

Once a file has "use client", everything it imports becomes part of the client bundle. So keep client components small and push them to the leaves. Don't slap "use client" on a big page just to make one button interactive — extract the button. Minimising the client boundary is a key performance skill.

Exercise · Split a page correctly

Build a product page where the product details are a Server Component (fetched on the server) and an "Add to cart" button with a quantity selector is a small Client Component island. Pass the product id from the server down to the client button as a prop. Verify in the Network tab that the page HTML arrives with data and only the button's JS is shipped.

🎓 Key takeaways

  • Server Components (default) render on the server, can be async + query the DB, ship zero JS.
  • Client Components ("use client") run in the browser and can use hooks/events.
  • Pattern: server shells with small client islands; pass server data down as props.
  • A Client Component can't import a Server Component, but can receive one as children.
  • "use client" is a boundary — keep it at the leaves to minimise the JS bundle.
