Data Fetching, Caching & PPR

🌐 Full-stack ⏱️ ~30 min ⚡ Render strategies

Next.js gives you fine control over when and how data is fetched and cached — static at build time, dynamic per request, or revalidated on a schedule. Choosing the right strategy per route is how you make apps both fast and fresh. We'll cover the rendering modes, caching, streaming with Suspense, and Partial Pre-rendering (PPR).

1. Static, dynamic & revalidation

caching.tsxtsx 
// STATIC (default): rendered once at build time, served instantly to everyone.
async function getPosts() {
  const res = await fetch("https://api/posts"); // cached by default
  return res.json();
}

// REVALIDATED (ISR): re-generate at most every 60s — fresh-ish + fast.
async function getPrices() {
  const res = await fetch("https://api/prices", { next: { revalidate: 60 } });
  return res.json();
}

// DYNAMIC: fetched fresh on every request (e.g. per-user data).
async function getCart() {
  const res = await fetch("https://api/cart", { cache: "no-store" });
  return res.json();
}
// On-demand: revalidatePath("/posts") / revalidateTag("posts") after a mutation.
One fetch option controls the whole strategy. Default caching makes routes static (fastest); next: { revalidate: N } gives Incremental Static Regeneration (fresh every N seconds); cache: "no-store" forces dynamic per-request rendering. After a write, revalidatePath/revalidateTag purge the cache on demand. Pick per data source.

2. Streaming with Suspense

streaming.tsxtsx 
import { Suspense } from "react";

export default function Page() {
  return (
    <main>
      <Header />                       {/* fast — renders immediately */}
      <Suspense fallback={<FeedSkeleton />}>
        <SlowFeed />                   {/* streams in when its data resolves */}
      </Suspense>
    </main>
  );
}
async function SlowFeed() {
  const items = await getSlowData();   // doesn't block the rest of the page
  return <Feed items={items} />;
}
Streaming sends HTML progressively. The server flushes the fast parts immediately and streams the slow Suspense boundaries (05-03) as their data resolves — fast first paint, no all-or-nothing wait. This is the same Suspense you learned, now powering server-rendered streaming.

3. Partial Pre-rendering (PPR)

✨
2026 · The best of static + dynamic

Partial Pre-rendering lets a single route be mostly static (instant) with dynamic holes streamed in. The static shell is served from the edge immediately; the personalised parts (wrapped in Suspense) stream after. You no longer choose static or dynamic for a whole page — you get both, per-component. It's the headline rendering feature of modern Next.js.

⚡
Pro-tip · Combine with TanStack Query on the client

Server Components handle initial data; for client-side interactivity (refetching, mutations, optimistic updates), hydrate TanStack Query (Part 6) with the server-fetched data. Server for the first paint, Query for the live client experience — a common, powerful combo.

Exercise · Three strategies

Build three routes: a static marketing page, a blog index revalidated every 60s, and a dynamic per-user dashboard (cache: "no-store"). Add a Suspense-streamed "recommendations" section to the dashboard. Observe the differences in the Network tab and response headers.

🎓 Key takeaways

  • Control rendering per data source: static (default), revalidate: N (ISR), no-store (dynamic).
  • Purge caches on demand with revalidatePath/revalidateTag after mutations.
  • Streaming + Suspense flushes fast parts first and streams slow ones — fast first paint.
  • PPR serves a static shell instantly with dynamic holes streamed in — static + dynamic in one route.
  • Pair Server Components (initial data) with TanStack Query (client interactivity).
