End-to-End Type Safety with tRPC v11

🌐 Full-stack · pivotal ⏱️ ~32 min 🔗 No codegen

tRPC gives you a fully type-safe API between your server and client with zero code generation and no schemas to maintain — the types simply flow from the server to the client through TypeScript inference. Call a server procedure from the client and get autocomplete + type-checking on the inputs and outputs. It's the purest expression of "one language, end to end".

1. Define a router on the server

server/router.tstypescript 
import { initTRPC } from "@trpc/server";
import { z } from "zod";
import { db } from "./db.js";

const t = initTRPC.create();

export const appRouter = t.router({
  getPosts: t.procedure.query(() => db.post.findMany()),

  getPost: t.procedure
    .input(z.object({ id: z.number() }))          // Zod validates + types the input
    .query(({ input }) => db.post.findById(input.id)),

  createPost: t.procedure
    .input(z.object({ title: z.string().min(1) }))
    .mutation(({ input }) => db.post.create({ data: input })),
});

// The ONLY thing the client imports is this TYPE — no runtime code:
export type AppRouter = typeof appRouter;
A router is a tree of procedures — query (read) or mutation (write), each with a Zod-validated, typed input. Crucially, the client only imports the type AppRouter (erased at runtime). There's no OpenAPI spec, no generated SDK — the contract is the TypeScript type itself.

2. Call it from the client — fully typed

Posts.tsxtsx 
"use client";
import { trpc } from "@/lib/trpc"; // a client typed with <AppRouter>

function Posts() {
  // Autocompleted procedure names, typed inputs AND outputs — no fetch, no types:
  const posts = trpc.getPosts.useQuery();              // built on TanStack Query!
  const post = trpc.getPost.useQuery({ id: 1 });        // input type-checked
  const create = trpc.createPost.useMutation();

  if (posts.isPending) return <Spinner />;
  return (
    <>
      <ul>{posts.data!.map((p) => <li key={p.id}>{p.title}</li>)}</ul>
      <button onClick={() => create.mutate({ title: "New" })}>Add</button>
      {/* create.mutate({ titel: "x" }) ❌ compile error: typo in input */}
    </>
  );
}
The server's types are the client's types — automatically. Rename a procedure or change an input on the server, and every call site updates or errors instantly across the whole codebase. tRPC's React client is built on TanStack Query (06-03), so you get caching, loading states, and mutations for free. This is the same "single source of truth" idea as your P02 validator, applied to an entire API.

3. Context, middleware & auth

protected.tstypescript 
// Middleware that requires an authenticated user:
const isAuthed = t.middleware(({ ctx, next }) => {
  if (!ctx.user) throw new TRPCError({ code: "UNAUTHORIZED" });
  return next({ ctx: { user: ctx.user } }); // narrows ctx.user to non-null
});
const protectedProcedure = t.procedure.use(isAuthed);

export const appRouter = t.router({
  me: protectedProcedure.query(({ ctx }) => ctx.user), // ctx.user is guaranteed
});
Middleware composes auth, logging, and rate-limiting into reusable protectedProcedures. The context (ctx) carries per-request data (the user, db). After the auth middleware, ctx.user is type-narrowed to non-null — the type system enforces that protected procedures always have a user.
✨
2026 · tRPC vs Server Actions

Server Actions (07-04) are great for simple form mutations within Next.js. tRPC shines for a large, organised API with many procedures, shared between web + mobile, with middleware and subscriptions. They coexist — many apps use Server Actions for forms and tRPC for the broader data layer. Both deliver end-to-end type safety.

🎓 Key takeaways

  • tRPC gives end-to-end type safety with no codegen — the client imports only the server router type.
  • Procedures are query/mutation with Zod-validated, typed inputs.
  • The React client is built on TanStack Query — caching/loading/mutations for free.
  • Middleware + context compose auth/logging; auth middleware type-narrows the context.
  • Coexists with Server Actions; ideal for large shared APIs across web + mobile.
