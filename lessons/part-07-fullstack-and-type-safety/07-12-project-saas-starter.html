Architecture · pure core, framework at the edges

The same discipline as every project: the security and billing rules are pure functions you can test without a database, browser, or framework. Server Actions (07-04), tRPC procedures (07-07), and Drizzle queries (07-06) are thin wrappers that call this core. Test the core to death; keep the glue minimal.

1. Role-based permissions

src/server/permissions.ts (excerpt)typescript 
export type Role = "owner" | "admin" | "member" | "viewer";
const RANK: Record<Role, number> = { owner: 3, admin: 2, member: 1, viewer: 0 };

const REQUIRED: Record<Action, Role> = {
  "org:delete": "owner", "billing:manage": "owner",
  "member:invite": "admin", "project:create": "member", "project:view": "viewer",
};

export function can(role: Role, action: Action): boolean {
  return RANK[role] >= RANK[REQUIRED[action]];
}
// You can never act on someone of equal-or-higher rank than yourself:
export function canActOnMember(actor: Role, target: Role): boolean {
  return RANK[actor] > RANK[target];
}
An action→minimum-role matrix is the clean way to model RBAC. One can() function answers every "is this allowed?" question, and canActOnMember prevents an admin from removing an owner. These are pure — the test file checks every role against every action.

2. Billing rules (no money bugs)

src/server/billing.ts (excerpt)typescript 
export function canAddSeat(plan: Plan, currentSeats: number): boolean {
  return currentSeats < LIMITS[plan].maxSeats;
}
// Proration: charge only for the remaining days of the cycle.
export function prorateAddSeatsCents(plan: Plan, added: number, daysLeft: number, cycle = 30) {
  const fraction = Math.min(daysLeft, cycle) / cycle;
  return Math.round(added * LIMITS[plan].seatPriceCents * fraction);
}
Money math must be correct — so it's pure and tested. Plan limits gate seats/projects; proration charges fairly for mid-cycle changes. Working in integer cents (never floats) avoids rounding bugs, and branded types (02-08) could enforce cents-vs-dollars. Every branch has a test.

3. The typed procedure layer (mini-tRPC)

usage (api.test.ts)typescript 
const createProject = protectedProcedure       // requires auth
  .input(z.object({ name: z.string().min(1) })) // validates input (Zod)
  .mutation(({ ctx, input }) => {
    authorize(ctx.user.role, "project:create"); // ctx.user is non-null + typed
    return { id: "p1", name: input.name, orgId: ctx.user.orgId };
  });

// The three guarantees, tested:
await createProject.call({ user: null }, { name: "X" });        // → UNAUTHORIZED
await createProject.call(memberCtx, { name: "" });              // → BAD_REQUEST
await createProject.call(viewerCtx, { name: "Site" });          // → ForbiddenError
await createProject.call(memberCtx, { name: "Site" });          // ✅ success
This is tRPC (07-07) in miniature. protectedProcedure gates auth and type-narrows ctx.user to non-null; .input() validates with Zod and types the input; the resolver authorizes via the permissions core. The test proves all four paths. Swap this builder for real tRPC and the patterns are identical.

🎓 Key takeaways

  • A SaaS's security & billing logic should be pure functions — tested exhaustively, framework-free.
  • RBAC via an action→min-role matrix; never let someone act on an equal/higher rank.
  • Billing in integer cents with tested proration — no money bugs.
  • A typed procedure layer gates auth, validates input (Zod), and authorizes in the resolver — tRPC's model.
