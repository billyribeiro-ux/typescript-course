Next.js 15: The App Router Mental Model

🌐 Full-stack ⏱️ ~32 min 📁 File-based routing

So far your React apps run entirely in the browser. Next.js is a full-stack framework that runs React on the server too — for faster loads, better SEO, and the ability to talk directly to databases. The App Router is its modern foundation, built on React Server Components. This part takes you from client-only to true full-stack engineer.

1. File-based routing

app/ directorytext 
app/
  layout.tsx          → root layout (wraps everything; html/body)
  page.tsx            → "/"  (the home page)
  about/
    page.tsx          → "/about"
  products/
    page.tsx          → "/products"
    [id]/
      page.tsx        → "/products/:id"  (dynamic segment)
      loading.tsx     → Suspense fallback for this route
      error.tsx       → error boundary for this route
  api/
    health/route.ts   → "/api/health"  (a JSON endpoint)
// The FOLDER STRUCTURE is your routing. Special files have special roles.
Routes are folders; page.tsx makes a route public. Special files give you powerful primitives per-route: layout.tsx (shared shell, persists across navigation), loading.tsx (an automatic Suspense fallback — 05-03!), error.tsx (an automatic error boundary — 05-04!), and route.ts (API endpoints). [id] folders are dynamic params.

2. The big shift: Server Components by default

🧩
Concept · Components run on the server first

In the App Router, components are React Server Components (RSC) by default — they render on the server, can be async, and can fetch data or query a database directly. Only components that need interactivity (state, effects, event handlers) opt into the client with "use client". We go deep on this split next lesson; it's the core mental model.

3. A page that fetches on the server

app/products/page.tsxtsx 
// No "use client" → this is a Server Component. It can be async and fetch
// data directly. The browser never runs this code or downloads its JS.
export default async function ProductsPage() {
  const products = await db.product.findMany(); // query the DB right here!

  return (
    <main>
      <h1>Products</h1>
      <ul>
        {products.map((p) => (
          <li key={p.id}>{p.name} — ${p.price}</li>
        ))}
      </ul>
    </main>
  );
}
// HTML arrives fully rendered with data — fast first paint, great SEO,
// zero client JS for this component.
This is impossible in a client-only app. A Server Component can await a database query and render the result to HTML on the server. No loading spinner, no client-side fetch waterfall, no API layer needed for reads, and no database credentials shipped to the browser. The page arrives complete.

4. Layouts & navigation

app/layout.tsxtsx 
import Link from "next/link";

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="en">
      <body>
        <nav>
          <Link href="/">Home</Link>
          <Link href="/products">Products</Link>
        </nav>
        {children}   {/* the active page renders here */}
      </body>
    </html>
  );
}
// next/link prefetches routes for instant navigation. Layouts persist
// across navigations (the nav doesn't re-render when you change pages).
Layouts compose and persist. The root layout wraps every page; nested layout.tsx files wrap their route segments. next/link does client-side navigation with automatic prefetching. Note: this is the same routing tree idea as React Router (06-01), but driven by your folder structure and server-rendered by default.

🎓 Key takeaways

  • Next.js runs React on the server + client — faster loads, SEO, direct DB access.
  • The App Router is file-based: folders are routes, page.tsx makes them public.
  • Special files: layout (shared shell), loading (Suspense), error (boundary), route.ts (APIs).
  • Components are Server Components by default — async, can fetch/query directly, ship no client JS.
  • next/link gives prefetched client navigation; layouts persist across pages.
