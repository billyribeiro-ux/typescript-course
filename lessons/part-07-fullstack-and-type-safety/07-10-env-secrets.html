Environment, Secrets & Configuration

🌐 Full-stack ⏱️ ~22 min 🔑 Config done safely

Every app has configuration that differs between environments — API keys, database URLs, feature flags. Handling these safely (never leaking secrets to the client) and type-safely (catching a missing or malformed variable at startup, not in production) is a hallmark of professional engineering. We'll use Zod to validate your environment.

1. The rules of secrets

  • Never commit secrets. Keep them in .env (gitignored) locally and in your host's secret store in production.
  • Server secrets stay on the server. In Next.js, only NEXT_PUBLIC_-prefixed vars reach the browser — everything else is server-only.
  • Commit a .env.example documenting required keys (with empty/placeholder values) so teammates know what to set.
⚠️
Gotcha · A leaked secret is compromised forever

If a secret is ever committed (even and then deleted), assume it's compromised and rotate it — it lives in git history and possibly in scrapers. Use a secret scanner in CI to block this before it happens. Treat secrets with paranoia.

2. Validate env at startup with Zod

env.tstypescript 
import { z } from "zod";

const envSchema = z.object({
  DATABASE_URL: z.string().url(),
  AUTH_SECRET: z.string().min(32),
  NODE_ENV: z.enum(["development", "production", "test"]).default("development"),
  NEXT_PUBLIC_APP_URL: z.string().url(),    // safe to expose (prefixed)
});

// Parse ONCE at startup — a missing/invalid var crashes immediately with a
// clear message, instead of a mysterious runtime failure in production:
export const env = envSchema.parse(process.env);
//     ^ env is now FULLY TYPED — env.NODE_ENV is the union, not string
This is your P02/Zod skills protecting your config. Parsing process.env with a schema does two things: it fails fast at startup if a required variable is missing or malformed (far better than a 3am production crash), and it gives you a fully-typed env object. Libraries like @t3-oss/env-nextjs add a clean client/server split on top.

3. Per-environment configuration

.env files
.env                # shared defaults (gitignored if it has secrets)
.env.local          # local overrides (ALWAYS gitignored)
.env.development    # dev-only
.env.production     # prod-only (real secrets live in the host's store)
.env.example        # COMMITTED — documents required keys, no real values

🎓 Key takeaways

  • Never commit secrets; use .env locally + the host's secret store in prod; commit only .env.example.
  • Only NEXT_PUBLIC_ vars reach the browser — everything else is server-only.
  • Validate env with Zod at startup — fail fast on missing/invalid vars, and get a typed env object.
  • Import the typed env, never raw process.env, throughout the app.
  • A leaked secret is compromised forever — rotate it and scan in CI.
