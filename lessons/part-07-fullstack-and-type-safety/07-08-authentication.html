Authentication & Sessions

🌐 Full-stack · critical ⏱️ ~32 min 🔐 Who are you?

Authentication (who you are) and authorization (what you can do) are foundational to any real app — and getting them wrong is dangerous. We'll cover the concepts (sessions vs JWTs, password hashing, OAuth), the modern libraries that handle the hard parts safely (Auth.js, Lucia, Clerk), and how to protect routes and Server Actions.

1. The core concepts

TermMeaning
AuthenticationVerifying identity (login)
AuthorizationChecking permissions (can this user do X?)
SessionServer-tracked login state, referenced by a cookie
JWTA signed token carrying claims, verifiable without a DB lookup
OAuth"Sign in with Google/GitHub" — delegating auth to a provider
⚠️
Gotcha · Never roll your own crypto

Always hash passwords with a slow, salted algorithm (bcrypt, argon2) — never store them or use fast hashes like MD5/SHA. Better still: use a vetted auth library and don't handle raw passwords at all. Auth bugs are security incidents; lean on battle-tested tools.

2. Use a library (Auth.js)

auth.tstypescript 
import NextAuth from "next-auth";
import GitHub from "next-auth/providers/github";
import { DrizzleAdapter } from "@auth/drizzle-adapter";
import { db } from "@/lib/db";

export const { handlers, auth, signIn, signOut } = NextAuth({
  adapter: DrizzleAdapter(db),        // store users/sessions in YOUR database
  providers: [GitHub],                // OAuth provider(s)
});

// In a Server Component / Action, get the current session:
// const session = await auth();
// if (!session?.user) redirect("/login");
Auth.js (NextAuth) handles the dangerous parts — OAuth flows, session cookies, CSRF protection — and stores users/sessions in your own database via the Drizzle adapter (07-06). You call auth() on the server to get the session. Alternatives: Lucia (lightweight, you own more), Clerk/WorkOS (hosted, fastest to ship).

3. Protecting routes & actions

protect.tsxtsx 
// Protect a page (Server Component):
export default async function Dashboard() {
  const session = await auth();
  if (!session?.user) redirect("/login");
  return <h1>Welcome, {session.user.name}</h1>;
}

// Protect a Server Action — ALWAYS check auth + authorization inside:
"use server";
export async function deletePost(id: number) {
  const session = await auth();
  if (!session?.user) throw new Error("Unauthorized");
  const post = await db.post.findById(id);
  if (post.authorId !== session.user.id) throw new Error("Forbidden"); // authz
  await db.post.delete(id);
}
Check authorization on the server, every time. Hiding a button in the UI is not security — a Server Action or Route Handler is a public endpoint (07-04). Verify the session and that this specific user is allowed to perform this specific operation (ownership/roles). Middleware can also guard whole route groups.

Set up Auth.js with a GitHub provider and the Drizzle adapter. Protect a /dashboard route (redirect to login if signed out). Add a Server Action that only lets a user edit their own profile — verify ownership inside the action and test that another user's id is rejected.

🎓 Key takeaways

  • Authentication = who you are; authorization = what you may do. Both matter.
  • Use a vetted library (Auth.js/Lucia/Clerk) — never roll your own crypto; hash with bcrypt/argon2.
  • Store users/sessions in your DB via an adapter; read the session with auth() on the server.
  • Always check auth + authorization inside Server Actions and Route Handlers — UI hiding isn't security.
  • Verify ownership/roles for each operation, not just "is logged in".
