Observability, Logging & Error Tracking

🏛️ Principal ⏱️ ~26 min 🔭 See production

We touched observability in Part 7; here we go deeper because owning production is core to senior+ work. Observability is your ability to answer "what is my app doing right now, and why?" without shipping new code to find out. Good observability turns mysteries into dashboards and 2am pages into quick fixes.

1. Structured logging

logging.tstypescript 
// ❌ Unstructured — impossible to search/filter at scale:
console.log("user " + userId + " bought " + sku);

// ✅ Structured — JSON logs you can query by field (pino/winston):
logger.info({ event: "purchase", userId, sku, amountCents, requestId }, "purchase completed");
// Include a requestId/traceId so you can follow ONE request across services.
// Log at appropriate levels: debug / info / warn / error.
Structured logs are searchable data, not prose. Logging objects (with a requestId/traceId) lets your log platform filter by user, event, or trace — essential when you have millions of lines. Never log secrets or PII. Use real log levels so you can dial verbosity per environment.

2. The three signals

SignalAnswersTool
Logs"What happened in this request?"pino + Datadog/Loki
Metrics"Is error rate/latency rising?"Prometheus/Datadog
Traces"Where did the time/error go across services?"OpenTelemetry

3. Alerting & SLOs

🚨
Concept · Alert on symptoms, define SLOs

An SLO (Service Level Objective) is a target like "99.9% of requests succeed in < 300ms". Alert on user-facing symptoms (error rate, latency, vitals) — not every internal blip — and tie alerts to an error budget (how much failure you can tolerate). This prevents both silent outages and alert fatigue. RUM (real user monitoring) ties it back to actual user experience and Core Web Vitals (08-05).

📝
Exercise · Instrument an app

Add a structured logger to a Next.js app with a per-request requestId. Wire Sentry for errors (07-11) and capture a custom breadcrumb on a key action. Define one SLO for an important endpoint and describe the alert you'd set. Confirm you can trace a single request end-to-end in your logs.

🎓 Key takeaways

  • Structured (JSON) logs with a trace/request id are searchable; never log secrets/PII.
  • The three signals: logs (what happened), metrics (trends), traces (across services).
  • Define SLOs and alert on user-facing symptoms tied to an error budget — avoid alert fatigue.
  • RUM connects observability to real user experience and Core Web Vitals.
  • Owning production — seeing it clearly — is core to senior+ engineering.
