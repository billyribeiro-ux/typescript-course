Building a Design System

🏛️ Principal ⏱️ ~36 min ✅ 9 + type tests

A design system is the shared component library + design tokens + conventions that keep a product consistent across teams. Building one is a hallmark of senior/principal work. We'll cover what goes into a design system, and build its type-safe styling core (a cn combiner + a cva variant API) in projects/p08-design-system/ — the exact primitives behind shadcn/ui + CVA, with tests proving both runtime and type behaviour.

1. What a design system contains

  • Design tokens: colours, spacing, typography, radii — the single source of style values (often CSS variables / a Tailwind theme).
  • Primitives: accessible, unstyled behaviour (Radix/React Aria — lesson 05-08).
  • Components: Button, Input, Dialog… built from primitives + tokens + variants.
  • Documentation: a living catalogue (Storybook) showing every component and state.
  • Conventions: naming, prop patterns (the asChild/polymorphism, slots), versioning (Changesets, Part 3).

2. The variant core (P08)

cva usagetypescript 
import { cva, type VariantProps } from "./src/index.js";

export const buttonVariants = cva("btn", {
  variants: {
    intent: { primary: "btn-primary", secondary: "btn-secondary", ghost: "btn-ghost" },
    size: { sm: "btn-sm", md: "btn-md", lg: "btn-lg" },
  },
  defaultVariants: { intent: "primary", size: "md" },
  compoundVariants: [{ intent: "ghost", size: "lg", class: "btn-ghost-lg" }],
});

// Extract the component's typed props FROM the variant config:
type ButtonVariantProps = VariantProps<typeof buttonVariants>;
// { intent?: "primary" | "secondary" | "ghost"; size?: "sm" | "md" | "lg" }

buttonVariants({ intent: "ghost", size: "lg" }); // "btn btn-ghost btn-lg btn-ghost-lg"
One declaration encodes a component's entire styling API. The cva function holds the base class, named variant groups, defaults, and compound variants (styles that apply only when several variants combine). VariantProps<typeof fn> uses a conditional type + infer (Part 2!) to extract the typed props — so your <Button> component gets autocompleted, type-checked variants for free.

3. Wrapping it in a component

Button.tsxtsx 
import { cn } from "./src/cn.js";
import { buttonVariants, type VariantProps } from "./src/index.js";
import type { ComponentProps } from "react";

type ButtonProps = ComponentProps<"button"> & VariantProps<typeof buttonVariants>;

export function Button({ intent, size, className, ...rest }: ButtonProps) {
  // cn merges the variant classes with any consumer overrides:
  return <button className={cn(buttonVariants({ intent, size }), className)} {...rest} />;
}
// <Button intent="ghost" size="lg" onClick={...}>Save</Button> — fully typed,
// supports all native button props (04-03) AND the design-system variants.
This is the canonical design-system component. It composes the native element props (ComponentProps<"button"> — 04-03), the variant props (VariantProps), and a className escape hatch merged via cn. Every shadcn/ui component follows exactly this shape. You now understand — and have built — the machinery.

🎓 Key takeaways

  • A design system = tokens + primitives + components + docs + conventions, shared across teams.
  • cva encodes a component's full styling API (base, variants, defaults, compound) in one declaration.
  • VariantProps<typeof fn> extracts typed props via conditional types + infer (Part 2).
  • The canonical component composes native props + variant props + a cn-merged className.
  • Ship it as a versioned monorepo package (Part 3) built on Radix + Tailwind — exactly like shadcn/ui.
