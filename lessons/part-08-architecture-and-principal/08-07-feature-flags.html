Feature Flags & Progressive Delivery

🏛️ Principal ⏱️ ~24 min 🚦 Ship safely

Feature flags decouple deploying code from releasing a feature. You can ship to production with a feature hidden, then turn it on for 1% of users, then 50%, then everyone — and flip it off instantly if something breaks. This is how mature teams ship constantly without fear. It's a superpower for risk management.

1. The basic flag

flags.tsxtsx 
// A flag gates a feature at runtime — config, not a redeploy:
function Checkout() {
  const newFlow = useFlag("new-checkout-flow"); // from LaunchDarkly/PostHog/etc.
  return newFlow ? <NewCheckout /> : <LegacyCheckout />;
}

// Flags can target by user, %, region, plan, or an experiment cohort:
//   "new-checkout-flow": { default: false, rollout: { internal: true, percent: 5 } }
// Turn it on for 5% of users; if error rates spike, flip to 0% instantly.
A flag is runtime config that gates code paths. Deploy the new checkout dark (off), enable it for internal users, then ramp the percentage while watching metrics (08-05/06). If something's wrong, disable it in seconds — no rollback deploy. This separates the risky moment (release) from the routine one (deploy).

2. Progressive delivery patterns

  • Canary release: route a small % of traffic to the new version; expand if healthy.
  • A/B test / experiment: show variants to cohorts and measure impact on a metric.
  • Kill switch: a flag to instantly disable a problematic feature or integration.
  • Trunk-based + flags: merge incomplete features behind a flag (off) to avoid long-lived branches.
⚠️
Gotcha · Flags are debt — clean them up

Every flag is a branch in your code and a config to maintain. Once a feature is fully rolled out, remove the flag and the dead path. Stale flags accumulate into a confusing mess ("flag debt"). Track them and schedule cleanup, just like any technical debt.

Exercise · Gate and ramp a feature

Add a simple flag system (a typed config or PostHog) to gate a new UI. Implement targeting by a user attribute and a percentage rollout. Add a "kill switch" path. Then write the cleanup ticket you'd file once the feature is at 100%.

🎓 Key takeaways

  • Feature flags decouple deploy from release — ship dark, ramp gradually, flip off instantly.
  • Target by user/%/region/cohort; ramp while watching metrics for safe rollouts.
  • Patterns: canary, A/B experiments, kill switches, and trunk-based merging behind flags.
  • Flags are debt — remove them and the dead path once a feature is fully rolled out.
  • This is how mature teams ship continuously with low risk.
