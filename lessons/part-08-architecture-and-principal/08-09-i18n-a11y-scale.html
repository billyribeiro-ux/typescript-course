i18n & Accessibility at Scale

🏛️ Principal ⏱️ ~26 min 🌍 For everyone, everywhere

To serve a global audience, an app must speak users' languages (i18n) and work for users with disabilities (a11y, deepened from 05-09). Retrofitting either is painful; designing for both from the start is a senior habit. This lesson covers doing them systematically across a large app.

1. Internationalization done right

i18n.tsxtsx 
// ❌ Hard-coded, un-translatable, and wrong for other locales:
<p>You have {count} messages</p>

// ✅ Externalized message with pluralization + interpolation:
const t = useTranslations();
<p>{t("inbox.count", { count })}</p>
// en: "{count, plural, =0 {No messages} one {# message} other {# messages}}"
// Libraries: next-intl, react-i18next, FormatJS. ICU MessageFormat handles
// plurals, gender, and ordinals correctly per language.
i18n is more than translating strings. Pluralization rules differ by language (some have 4+ plural forms), and you must format dates, numbers, and currencies per locale (Intl.DateTimeFormat/Intl.NumberFormat). Externalize every string to message files, support RTL layouts (Arabic/Hebrew) with logical CSS properties, and never concatenate translated fragments.

2. Accessibility as a system

  • Bake it into the design system (P08): accessible primitives (Radix/React Aria) mean every consuming app inherits a11y for free.
  • Automate: eslint-plugin-jsx-a11y in CI, axe checks in tests (05-10), and contrast checks in design tokens.
  • Test with real assistive tech periodically — keyboard-only, screen readers — and include people with disabilities in research.
  • Set a standard: target WCAG 2.2 AA; make it part of "definition of done".
🧩
Concept · Accessibility is a feature, and the law

In many jurisdictions, accessibility is a legal requirement (ADA, the European Accessibility Act). Beyond compliance, it expands your market and improves UX for everyone (captions help in noisy rooms; keyboard nav helps power users). Treat it as a first-class quality attribute, not a checkbox.

📝
Exercise · Internationalize + audit

Add next-intl (or react-i18next) to an app: externalize all strings, add a second locale, and format a date + number per locale with Intl. Then run an axe audit, fix the issues, and verify the UI works in an RTL locale with logical CSS properties.

🎓 Key takeaways

  • i18n = externalized strings + correct pluralization (ICU) + locale-aware Intl formatting + RTL support.
  • Never concatenate translated fragments or hard-code user-facing text.
  • Make accessibility systemic: accessible design-system primitives, automated checks in CI, real AT testing.
  • Target WCAG 2.2 AA as a definition-of-done; it's often a legal requirement.
  • Both i18n and a11y are far cheaper designed-in than retrofitted.
