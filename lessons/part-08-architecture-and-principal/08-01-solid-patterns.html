SOLID & Design Patterns in TypeScript

🏛️ Principal ⏱️ ~32 min 🧱 Maintainable code

You can build features; now you'll learn to build them so they stay maintainable for years and across teams. SOLID is five timeless principles for structuring code, and design patterns are reusable solutions to common problems. Applied with judgement (not dogma), they're how you write code that's a pleasure to extend rather than a fragile mess.

1. The SOLID principles

PrincipleIn one line
Single ResponsibilityA module should have one reason to change.
Open/ClosedOpen for extension, closed for modification.
Liskov SubstitutionSubtypes must be usable wherever their base type is.
Interface SegregationMany small interfaces beat one fat one.
Dependency InversionDepend on abstractions, not concretions.

2. Dependency Inversion in practice

dependency-inversion.tstypescript 
// ❌ High-level code depends on a concrete implementation:
class OrderService {
  private email = new SendgridClient(); // locked to Sendgrid; hard to test
  notify(o: Order) { this.email.send(o.email, "Shipped"); }
}

// ✅ Depend on an ABSTRACTION (interface). Inject the concrete one:
interface Mailer { send(to: string, body: string): Promise<void>; }

class OrderService2 {
  constructor(private mailer: Mailer) {}      // injected dependency
  async notify(o: Order) { await this.mailer.send(o.email, "Shipped"); }
}
// Now you can pass a SendgridMailer in production and a FakeMailer in tests —
// OrderService2 doesn't know or care which. Easy to test, easy to swap.
Dependency inversion is the most impactful SOLID principle for testability. By depending on a Mailer interface and injecting the implementation, you decouple your logic from external services. This is exactly why P01–P07 kept logic pure and pushed I/O to the edges — the same idea, formalised. The compiler enforces the contract.

3. Useful patterns (used with judgement)

  • Strategy: swap algorithms behind a common interface (e.g. different pricing rules) — you just saw it with Mailer.
  • Factory: centralise object creation (e.g. createClient(config)).
  • Adapter: wrap a third-party API in your own interface so you can swap it later.
  • Observer: publish/subscribe — the basis of event systems and React state libraries.
  • Repository: abstract data access behind an interface (swap Drizzle for a mock in tests).
⚠️
Gotcha · Patterns are tools, not goals

Over-applying patterns creates needless abstraction ("AbstractFactoryStrategyManager"). Reach for a pattern when you feel real pain (duplication, rigidity, untestability) — not preemptively. The best code is as simple as the problem allows. Principal engineers add abstraction reluctantly and remove it eagerly.

⚡
Pro-tip · In React, patterns look different

React leans functional: dependency injection is often just props and context; strategy is passing a function; the repository pattern becomes a custom hook (useUsers()). The principles (single responsibility, depend on abstractions) matter more than the classic OOP forms. Apply the spirit.

📝
Exercise · Invert a dependency

Take a function that directly calls fetch and refactor it to accept a HttpClient interface. Write a real implementation and a fake one, and a test that uses the fake. Notice how the logic became trivially testable — that's SOLID paying off.

🎓 Key takeaways

  • SOLID: single responsibility, open/closed, Liskov substitution, interface segregation, dependency inversion.
  • Dependency inversion (depend on interfaces, inject implementations) is the key to testable, swappable code.
  • Patterns (Strategy, Factory, Adapter, Observer, Repository) solve recurring problems — apply with judgement.
  • Don't over-abstract; reach for patterns when you feel real pain, and prefer simplicity.
  • In React the principles hold, but the forms are functional (props/context/hooks).
