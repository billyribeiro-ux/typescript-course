Performance Budgets & Core Web Vitals

🏛️ Principal ⏱️ ~28 min 📏 Measure what matters

Performance is a feature — it affects conversion, SEO, and accessibility. Google's Core Web Vitals are the industry-standard metrics for user-perceived speed, and a performance budget is how you keep them from regressing as the app grows. This is how senior engineers make performance a measurable, enforced commitment rather than a vague aspiration.

1. Core Web Vitals

MetricMeasuresGood
LCP (Largest Contentful Paint)Loading: when the main content appears< 2.5s
INP (Interaction to Next Paint)Responsiveness: lag after interactions< 200ms
CLS (Cumulative Layout Shift)Stability: unexpected layout jumps< 0.1
🧩
Concept · Field vs lab data

Lab data (Lighthouse) is a controlled test — great for debugging. Field data (real users, via the Chrome UX Report / web-vitals library) is what actually counts and what Google ranks on. Optimise in the lab, but verify with field data — your users have slower devices and networks than your laptop.

2. Common fixes mapped to vitals

  • LCP: optimise the hero image (modern formats, responsive sizes, priority loading), server-render/stream (Part 7), reduce render-blocking resources.
  • INP: break up long tasks, use transitions (05-05), avoid heavy synchronous work in handlers, ship less JS.
  • CLS: reserve space for images/ads (width/height), avoid inserting content above existing content, use font-display strategies.

3. A performance budget in CI

budget enforcementjson 
// A budget defines limits CI enforces — a PR that exceeds them fails:
{
  "budgets": [
    { "type": "bundle", "name": "main", "maximumWarning": "150kb", "maximumError": "200kb" },
    { "metric": "LCP", "budget": 2500 },
    { "metric": "CLS", "budget": 0.1 }
  ]
}
// Tools: Lighthouse CI, bundlesize, size-limit. Run them in the CI gate (03-09)
// so performance regressions are caught in the PR, not in production.
A budget turns performance into an enforceable contract. Set limits on bundle size and vitals; wire a tool (Lighthouse CI, size-limit) into your CI (03-09) so a PR that blows the budget is blocked. Without enforcement, performance silently erodes one "small" dependency at a time.
📝
Exercise · Audit and budget

Run Lighthouse on a project and note its LCP/INP/CLS. Add the web-vitals library to log field metrics. Set a size-limit budget on the main bundle and add it to CI. Then make one improvement (e.g. lazy-load a heavy component) and confirm the metric improves.

🎓 Key takeaways

  • Core Web Vitals: LCP (loading), INP (responsiveness), CLS (stability) — with target thresholds.
  • Trust field data (real users) over lab data; users have slower devices than you.
  • Map fixes to metrics: image/streaming for LCP, less JS/transitions for INP, reserved space for CLS.
  • A performance budget enforced in CI blocks regressions before they ship.
  • Performance is a measurable, owned commitment — not a vague aspiration.
