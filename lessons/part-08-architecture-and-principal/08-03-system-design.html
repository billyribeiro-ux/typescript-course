Frontend System Design & Scalability

🏛️ Principal ⏱️ ~34 min 🗺️ Big-picture thinking

At senior+ levels, you're asked to design systems, not just implement tickets — and frontend system design is a staple interview at Meta/Google/etc. The skill: take a vague problem ("design a news feed"), clarify requirements, and reason through the architecture, data flow, performance, and trade-offs out loud. This lesson gives you the framework.

1. The system-design framework

  1. Clarify requirements. Functional (what it does) and non-functional (scale, latency, devices, offline, a11y, i18n). Never start coding in your head before you know the constraints.
  2. Define the data model & API. What entities exist? What does the client fetch, and how (REST/GraphQL/tRPC, pagination, real-time)?
  3. Component architecture. Break the UI into components and decide where state lives (server vs client; which library — Part 6).
  4. Address the hard parts. Performance, caching, optimistic updates, error/empty/loading states, accessibility.
  5. Discuss trade-offs. There's no perfect answer — articulate what you'd optimise for and why.

Concept · Every answer ties back to what you've learned

Notice that the feed design is just the course's techniques composed: TanStack Query for data, virtualization for performance, optimistic updates for UX, error boundaries for resilience. System design isn't new magic — it's knowing which tools to combine and why.

3. Scalability concerns at the frontend

  • Bundle size: code splitting, lazy routes, tree-shaking, careful dependency choices.
  • Rendering strategy: static vs SSR vs streaming vs client (Part 7) per page's needs.
  • Caching layers: CDN, server cache, query cache, browser cache — know which solves which problem.
  • Team scale: module boundaries, a design system, and conventions so many engineers can work without colliding (micro-frontends next lesson).
📝
Exercise · Design out loud

Pick a product (autocomplete search, a chat app, a Google-Docs-style editor, an analytics dashboard). Spend 30 minutes writing a design doc: requirements, data/API, component tree + state placement, performance plan, and the top three trade-offs. Practise narrating your reasoning — that's what interviews assess.

🎓 Key takeaways

  • Frontend system design follows a framework: clarify → data/API → components/state → hard parts → trade-offs.
  • Capture non-functional requirements (scale, latency, devices, a11y, i18n), not just features.
  • Great designs compose the course's tools (Query, virtualization, optimistic UI, boundaries).
  • Scalability spans bundle size, rendering strategy, caching layers, and team/module boundaries.
  • Practise narrating trade-offs — there's no single right answer, and that's the point.
