API Design, Contracts & Versioning

🏛️ Principal ⏱️ ~28 min 🤝 Contracts between teams

An API is a contract that many clients depend on — changing it carelessly breaks people. Designing APIs that are intuitive, consistent, and evolvable is a core senior+ skill, whether you're building REST endpoints, a GraphQL schema, or tRPC procedures. This lesson covers the principles that apply across all of them.

1. Principles of good API design

  • Consistent & predictable: uniform naming, casing, error shapes, and pagination across every endpoint.
  • Right granularity: not too chatty (N+1 round-trips), not a single mega-endpoint.
  • Explicit errors: machine-readable codes + human messages; consistent status codes.
  • Pagination & filtering: cursor-based for large/real-time lists; documented limits.
  • Idempotency: safe retries for mutations (idempotency keys) — networks are unreliable.

2. REST vs GraphQL vs tRPC

StyleBest when
RESTPublic APIs, simple resources, broad client compatibility, caching by URL
GraphQLMany clients with varied data needs; avoid over/under-fetching
tRPCInternal TypeScript apps wanting end-to-end types with zero codegen (07-07)

3. Contracts & evolution

🤝
Concept · Schema-as-contract + backward compatibility

Define the contract explicitly — a Zod schema (your P02!), OpenAPI spec, or GraphQL/tRPC types — and share it so clients and server agree. Evolve additively: add optional fields, never remove or repurpose existing ones without a version bump. Deprecate with warnings and a timeline; only remove after clients migrate. For breaking changes, version (/v2) and run both for a transition window.

⚠️
Gotcha · A field rename is a breaking change

Renaming name → fullName, tightening a type, or making an optional field required all break existing clients. Treat your published API as immutable; add the new shape alongside the old, migrate clients, then remove. Internal type safety (tRPC) helps you find breakages, but external consumers still need a migration path.

📝
Exercise · Design + evolve an API

Design a small "tasks" API: define the resource, list endpoint with cursor pagination, a consistent error shape, and a Zod contract. Then write down how you'd add a new required field without breaking existing clients (hint: add it optional, default it, deprecate the old behaviour, then tighten in v2).

🎓 Key takeaways

  • Good APIs are consistent, right-grained, explicit about errors, paginated, and idempotent for mutations.
  • Choose REST (public/cacheable), GraphQL (varied clients), or tRPC (internal TS, zero codegen).
  • Make the schema the contract (Zod/OpenAPI/types) and share it between client and server.
  • Evolve additively; renames/removals are breaking — deprecate, version, and migrate.
  • Treat a published API as a long-term commitment to your consumers.
