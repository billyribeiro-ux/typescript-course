Micro-Frontends & Module Federation

🏛️ Principal ⏱️ ~26 min 🧩 Team-scale architecture

When a single app is built by dozens of teams, one giant codebase and deploy becomes a bottleneck. Micro-frontends split a frontend into independently-developed, independently-deployed pieces — each team owns theirs end-to-end. It's a powerful but heavy architecture; knowing when (and when not) to use it is the principal-level skill.

1. The idea & the approaches

ApproachHow
Route-basedDifferent apps own different URL paths (reverse proxy routes to each)
Build-timeTeams publish packages; a shell composes them (simpler, coupled deploys)
Module FederationApps load each other's code at runtime over the network
Web ComponentsFramework-agnostic custom elements as the integration boundary

2. Module Federation in one breath

🧩
Concept · Runtime code sharing

Module Federation (Webpack/Rspack, and Vite plugins) lets a "host" app load a "remote" app's components at runtime — each deployed separately, sharing dependencies (one copy of React). The checkout team ships their Checkout remote; the shell consumes it without rebuilding. Teams deploy on their own cadence.

3. The trade-offs (read this twice)

  • Wins: team autonomy, independent deploys, isolated failure, tech flexibility per team.
  • Costs: operational complexity, version/dependency drift, larger total payload, cross-app consistency (shared design system becomes essential), harder end-to-end testing and debugging.
⚠️
Gotcha · Most teams don't need this

Micro-frontends solve an organizational scaling problem (many teams, one product), not a technical one. For a single team, a well-structured monorepo (Part 3) with clear module boundaries gives most of the benefit with far less pain. Reach for micro-frontends only when team coordination is the real bottleneck — and say so in interviews.

📝
Exercise · Decide and justify

For three scenarios — a 5-person startup, a 200-engineer e-commerce platform, and a bank with strict team isolation — decide whether you'd use a monorepo or micro-frontends, and write one paragraph justifying each choice with the trade-offs. The reasoning is the deliverable.

🎓 Key takeaways

  • Micro-frontends split a frontend into independently-built/deployed pieces owned by separate teams.
  • Approaches: route-based, build-time, Module Federation (runtime), Web Components.
  • They buy team autonomy at the cost of operational complexity and consistency challenges.
  • It's an organizational solution — most teams are better served by a structured monorepo.
  • Knowing when not to adopt them is the senior signal.
