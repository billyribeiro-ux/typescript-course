Modules, Namespaces & Declaration Files

🎯 Core ⏱️ ~24 min 📦 Organising code

As projects grow, how you split and connect files becomes architecture. This lesson covers ES modules in TypeScript (with the all-important import type), what .d.ts declaration files are, why namespaces are mostly legacy, and how types travel with your published code.

1. ES modules with types

user.tstypescript 
// user.ts — export both values and types
export interface User {
  id: number;
  name: string;
}
export function createUser(name: string): User {
  return { id: Date.now(), name };
}
export const MAX_NAME_LEN = 50;
A module exports values (functions, constants) and types (interfaces, type aliases) side by side. Anything not exported is private to the file.
app.tstypescript 
// Import VALUES normally; import TYPES with `import type`:
import { createUser, MAX_NAME_LEN } from "./user.js";
import type { User } from "./user.js";

const u: User = createUser("Ada");

// Inline form also works and is encouraged with verbatimModuleSyntax:
import { createUser as make, type User as U } from "./user.js";
import type matters: it marks an import as types-only, so it's fully erased from the compiled JavaScript. With verbatimModuleSyntax (which we enabled in P01), this is required and keeps your output lean and your imports honest about what's a runtime dependency vs a compile-time one.
⚠️
Gotcha · The .js extension in imports

Under Node's ESM ("module": "NodeNext"), you import with the .js extension even though the file is .ts — because you're importing the compiled output. It looks odd at first but is correct. Bundlers like Vite are more relaxed and let you omit extensions.

2. Declaration files (.d.ts)

A declaration file contains only types — no implementation. It's how a compiled JavaScript library ships its type information so consumers get full IntelliSense. When you pnpm add a typed package, you're getting its .d.ts files.

shapes.d.tstypescript 
// A .d.ts only DECLARES — no function bodies, no runtime code.
export declare function distance(a: Point, b: Point): number;
export interface Point { x: number; y: number; }

// Ambient declaration for an untyped global or env variable:
declare global {
  interface Window {
    analytics?: { track(event: string): void };
  }
}
export {}; // makes this a module
You'll generate .d.ts files automatically (we set "declaration": true in P01's tsconfig) when publishing a library, so consumers get your types. You'll occasionally write them by hand to type a plain-JS dependency or a global. For packages lacking types, the community ships @types/... packages from DefinitelyTyped.

3. Namespaces (legacy — know, don't use)

namespaces.tstypescript 
// Namespaces predate ES modules. You'll see them in old code and some libs.
namespace Geometry {
  export function area(r: number) { return Math.PI * r * r; }
}
Geometry.area(2);

// ✅ Modern equivalent is just a module file with exports — use that instead.
// Namespaces don't tree-shake well and don't fit the ESM world.
Guidance: recognise namespaces in legacy/library code, but always reach for ES modules in your own work. Files are your namespaces now.

Exercise · Split a module

Take any single-file exercise from earlier and split it into two files: one exporting a type and a function, another importing them. Use import type for the type. Build it with tsc and confirm the emitted JS contains no trace of the type import.

🎓 Key takeaways

  • Modules export values and types together; non-exports are file-private.
  • Use import type for type-only imports — required under verbatimModuleSyntax, keeps output lean.
  • Under NodeNext ESM, import with the .js extension (the compiled output).
  • .d.ts files carry types for compiled JS; @types/* packages add types to untyped libs.
  • Namespaces are legacy — use ES module files instead.
