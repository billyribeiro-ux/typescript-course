Generics From First Principles

🎯 Core · pivotal ⏱️ ~32 min 🧬 Reusable type logic

Generics are the feature that intimidates beginners and defines experts. The idea is simple: a generic is a type that takes a type as a parameter — a function or type with a "hole" that the caller fills in. They let you write code that's both fully reusable and fully type-safe. Every serious library — React, TanStack Query, Zod — is built on them.

1. The problem generics solve

why-generics.tstypescript 
// Without generics, you either lose type info...
function firstAny(arr: any[]): any {
  return arr[0]; // returns `any` — all safety gone
}
const x = firstAny(["a", "b"]); // x is `any` 😱

// ...or you duplicate the function per type (unmaintainable):
function firstString(arr: string[]): string { return arr[0]!; }
function firstNumber(arr: number[]): number { return arr[0]!; }

// Generics give you ONE function that preserves the exact type:
function first<T>(arr: T[]): T | undefined {
  return arr[0];
}
const a = first(["a", "b"]); // a is string | undefined
const b = first([1, 2, 3]);  // b is number | undefined
// T is INFERRED from the argument — you rarely write it explicitly.
The mental model: <T> declares a type variable — a placeholder filled in per call. first(["a"]) sets T = string; first([1]) sets T = number. One implementation, perfect types for every caller. And note: you didn't specify T — it was inferred.

2. Generic constraints with extends

Often a generic shouldn't accept any type — only types with certain properties. The extends keyword constrains the type parameter.

constraints.tstypescript 
// "T must have a length property":
function longest<T extends { length: number }>(a: T, b: T): T {
  return a.length >= b.length ? a : b;
}
longest("hello", "hi");       // ✅ strings have length → "hello"
longest([1, 2, 3], [1]);      // ✅ arrays have length
// longest(10, 20);           // ❌ numbers have no length

// The classic: a fully type-safe property getter.
function getProp<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}
const user = { name: "Ada", age: 36 };
const name = getProp(user, "name"); // typed as string
const age = getProp(user, "age");   // typed as number
// getProp(user, "email");          // ❌ "email" is not a key of user
This is a defining example. K extends keyof T means "K is one of T's keys", and T[K] is "the type of that key's value". The result: a getter that knows user.name is a string and user.age is a number, and rejects invalid keys. keyof and indexed access (T[K]) are the gateway to Part 2's wizardry.

3. Generic types & interfaces

generic-types.tstypescript 
// A generic data structure:
interface Box<T> {
  value: T;
}
const stringBox: Box<string> = { value: "hi" };

// A generic API envelope you'll reuse constantly:
type ApiResponse<T> = {
  data: T;
  status: number;
  timestamp: string;
};
type UserResponse = ApiResponse<{ id: number; name: string }>;

// Defaults and multiple parameters:
type Dictionary<V, K extends string = string> = Record<K, V>;
type Pair<A, B> = { first: A; second: B };
const p: Pair<string, number> = { first: "age", second: 36 };
Generic types parameterise data shapes the way generic functions parameterise logic. ApiResponse<T> is one definition that gives you a typed envelope for any payload — write it once, reuse it for every endpoint. Type parameters can have defaults (= string) too.

4. A real, reusable utility

groupBy.tstypescript 
// Group an array of items by a derived key — fully typed.
function groupBy<T, K extends string | number>(
  items: readonly T[],
  getKey: (item: T) => K
): Record<K, T[]> {
  const result = {} as Record<K, T[]>;
  for (const item of items) {
    const key = getKey(item);
    (result[key] ??= []).push(item);
  }
  return result;
}

const people = [
  { name: "Ada", city: "Lisbon" },
  { name: "Lin", city: "Lisbon" },
  { name: "Sam", city: "Madrid" },
];
const byCity = groupBy(people, (p) => p.city);
// byCity is Record<string, { name: string; city: string }[]>
console.log(byCity.Lisbon.length); // 2
This is the payoff: one generic function, zero any, perfect inference for any element type and any key function. This is precisely the calibre of utility you'll build into a published library in Project P02 — and it's only the warm-up for Part 2.
⚡
Pro-tip · Don't over-genericise

Reach for a generic when a function genuinely works over many types and must preserve them. If a parameter is always a string, just type it string. Premature generics make code harder to read for no benefit. Power, applied with judgement.

📝
Exercise · Type-safe pluck

Write function pluck<T, K extends keyof T>(items: T[], key: K): T[K][] that maps an array of objects to an array of one property's values. Verify pluck(people, "name") is typed as string[] and pluck(people, "nope") is a compile error.

🎓 Key takeaways

  • A generic <T> is a type parameter — a hole the caller fills, usually by inference.
  • Generics preserve exact types where any would discard them.
  • Constrain with T extends ...; K extends keyof T + T[K] give type-safe key access.
  • Generic types/interfaces parameterise data shapes (e.g. ApiResponse<T>).
  • Use generics when they earn their keep; don't genericise constants.
