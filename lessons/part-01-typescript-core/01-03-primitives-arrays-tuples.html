Primitives, Arrays, Tuples & Enums

🎯 Core ⏱️ ~26 min 🔤 The type vocabulary

Every type you'll ever build is composed from a small set of primitives and collection types. This lesson is your vocabulary lesson: how to annotate primitives, type arrays and read-only arrays, model fixed-length tuples, and when (and when not) to use enums — including the modern alternative professionals now prefer.

1. Annotating primitives

primitives.tstypescript 
// Explicit annotations (the type after the colon):
const name: string = "Ada";
const age: number = 36;
const active: boolean = true;
const nothing: null = null;
const missing: undefined = undefined;
const big: bigint = 100n;

// But prefer INFERENCE — let TS derive the type from the value:
const city = "Lisbon";   // inferred: string (no annotation needed)
let count = 0;           // inferred: number

// Annotate when there's no value to infer from (e.g. function params):
function greet(person: string): string {
  return `Hi, ${person}`;
}
Rule of thumb: don't annotate what TypeScript can infer. Annotate function parameters, return types you want to lock down, and variables declared without an initial value. Over-annotating is noise; the compiler is smarter than you think.

2. Arrays and readonly arrays

arrays.tstypescript 
const scores: number[] = [90, 85, 100];      // array of numbers
const names: Array<string> = ["Ada", "Lin"];  // identical, generic syntax

// readonly arrays can't be mutated — great for function inputs:
function total(values: readonly number[]): number {
  // values.push(1);  // ❌ Error: push doesn't exist on readonly arrays
  return values.reduce((sum, n) => sum + n, 0);
}

// Arrays of objects — the everyday shape:
type Todo = { id: number; title: string; done: boolean };
const todos: Todo[] = [
  { id: 1, title: "Learn types", done: false },
];
readonly T[] is underused and powerful. Marking a function's array parameter readonly documents "I won't mutate your data" and lets the compiler enforce it — exactly the immutable discipline from Part 0, now guaranteed by types.

3. Tuples: fixed-length, positional types

A tuple is an array with a fixed length where each position has its own type. They shine for pairs, coordinates, and — famously — React's useState return value.

tuples.tstypescript 
// A tuple: exactly [string, number]
const person: [name: string, age: number] = ["Ada", 36];
const personName = person[0]; // string
const personAge = person[1];  // number

// Returning a tuple — the useState pattern you'll see constantly in React:
function useToggle(initial: boolean): [boolean, () => void] {
  let value = initial;
  const toggle = () => { value = !value; };
  return [value, toggle];
}
const [isOpen, toggleOpen] = useToggle(false);

// Named tuple labels (name:, age:) are just for readability in tooltips.
Why React uses tuples: const [count, setCount] = useState(0) returns a tuple — position 0 is the value, position 1 is the setter. Tuples let you destructure with any names you like, which is why hooks feel so ergonomic.

4. Enums — and the modern alternative

An enum names a set of related constants. TypeScript has a built-in enum, but it has real downsides (it generates runtime code and has surprising behaviours). The modern, widely-preferred approach is a union of string literals, often with as const.

enums.tstypescript 
// Classic enum (generates runtime code):
enum Direction { Up, Down, Left, Right }
const move: Direction = Direction.Up;

// ✅ Preferred in 2026: a string-literal union (zero runtime cost):
type DirectionT = "up" | "down" | "left" | "right";
const move2: DirectionT = "up";
// const bad: DirectionT = "diagonal"; // ❌ not assignable

// The "const object + union" pattern — the best of both worlds:
const Status = {
  Idle: "idle",
  Loading: "loading",
  Done: "done",
} as const;
type Status = (typeof Status)[keyof typeof Status]; // "idle" | "loading" | "done"

const s: Status = Status.Loading; // "loading"
Principal-level guidance: reach for string-literal unions by default — they are zero-cost, tree-shakeable, serialise cleanly to JSON, and play perfectly with narrowing. The as const object pattern gives you named constants and a precise union type. We decode as const, typeof, and keyof fully in Part 2.
⚠️
Gotcha · Avoid numeric enums for data

Numeric enums (enum E { A, B }) accept any number at assignment in some positions and store opaque integers in your data — a debugging nightmare when you see status: 2 in a database. String-literal unions store readable values. Prefer them.

📝
Exercise · Model a traffic light

Create a string-literal union Light = "red" | "amber" | "green" and a function next(light: Light): Light that returns the next light in the cycle. Make the function return type Light so the compiler guarantees you never return an invalid colour.

🎓 Key takeaways

  • Annotate primitives only when there's nothing to infer from; trust inference otherwise.
  • T[] or Array<T> for arrays; use readonly T[] for inputs you won't mutate.
  • Tuples are fixed-length positional types — the basis of useState's [value, setter].
  • Prefer string-literal unions over enum — zero-cost and JSON-friendly.
  • The as const object + union pattern gives named constants and a precise type.
