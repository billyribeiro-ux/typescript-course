unknown, any, never & Type Assertions

🎯 Core ⏱️ ~24 min 🛡️ The escape hatches

The type system has three special "top and bottom" types — any, unknown, and never — plus assertions that let you override the compiler. Used wisely, these are the difference between safe boundaries and silent holes. A principal engineer knows exactly when each is appropriate and treats any as a code smell.

1. any — the safety off-switch

any.tstypescript 
let value: any = "hello";
value.foo.bar.baz();    // compiles — and CRASHES at runtime. No safety at all.
value = 42;             // anything goes
const n: number = value; // silently assigns — `any` infects everything it touches

// `any` disables type-checking for that value AND anything derived from it.
// It is almost never the right answer. Treat each `any` as a TODO.
any is contagious and dangerous: it switches off the compiler for that value and silently spreads. In strict codebases, any is banned by lint rules. When you think you need it, you almost always want unknown instead.

2. unknown — the safe top type

unknown.tstypescript 
// unknown can hold anything (like any), but you can DO nothing with it
// until you prove what it is. It's "any with a seatbelt."
function handle(input: unknown) {
  // input.toUpperCase();  // ❌ not allowed — we don't know it's a string
  if (typeof input === "string") {
    return input.toUpperCase(); // ✅ narrowed to string first
  }
  return String(input);
}

// The right type for data from outside your program:
function parseJSON(text: string): unknown {
  return JSON.parse(text); // honestly typed — you must validate before use
}
const data = parseJSON('{"id":1}');
// You'd now use a type guard (01-06) to safely narrow `data`.
This is the lesson: use unknown at every boundary where untyped data enters — JSON.parse, fetch bodies, form inputs, catch errors. It forces you to validate before use, turning a runtime risk into a compile-time requirement. P01's parseTasks does exactly this.

3. never — the impossible type

never.tstypescript 
// `never` = a value that can never exist. Returned by functions that never finish:
function fail(message: string): never {
  throw new Error(message); // never returns normally
}

// Its superpower is exhaustiveness checking (from 01-06):
type Method = "GET" | "POST";
function handle(m: Method) {
  switch (m) {
    case "GET": return "reading";
    case "POST": return "writing";
    default:
      const _exhaustive: never = m; // errors if a case is unhandled
      return _exhaustive;
  }
}
never is the bottom type — assignable to everything, nothing assignable to it (except never). It marks code paths that can't happen, which is exactly why it powers exhaustiveness checks and surfaces dead code.

4. Type assertions (as) — use with care

assertions.tstypescript 
// An assertion tells the compiler "trust me, it's this type." It does NO checking.
const el = document.getElementById("app") as HTMLCanvasElement;
// If #app isn't actually a canvas, this lies and you crash later.

// `as const` is the GOOD assertion — it narrows to literals, doesn't lie:
const routes = ["/home", "/about"] as const; // readonly ["/home", "/about"]

// The "non-null assertion" (!): "this is definitely not null/undefined."
const input = document.querySelector("input")!; // use only when you're certain

// AVOID `as any` and double assertions `as unknown as T` — they punch holes
// through the type system. Prefer type guards to PROVE types instead.
Assertions override the compiler without verifying anything — they're a promise you make, and the compiler believes you. Reserve them for cases you truly know better than the compiler (DOM types, as const). Prefer type guards, which actually check. Every as is a small trust debt; keep the balance low.

Exercise · Safe error handling

In a try/catch, the caught error is typed unknown in modern TS. Write a helper function toMessage(err: unknown): string that returns err.message when err instanceof Error, otherwise String(err). You've now handled errors the safe way — exactly what P01's index.ts does.

🎓 Key takeaways

  • any disables type-checking and spreads — treat every use as a smell to remove.
  • unknown is the safe top type: accept anything, but prove what it is before using it.
  • Use unknown at every untyped boundary (JSON, fetch, form input, caught errors).
  • never is the impossible type; it powers exhaustiveness checks and marks unreachable code.
  • Assertions (as, !) override without checking — prefer type guards; as const is the safe exception.
