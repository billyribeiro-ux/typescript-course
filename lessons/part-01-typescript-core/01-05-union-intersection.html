Union & Intersection Types

🎯 Core ⏱️ ~24 min ∪ ∩ Combining types

Unions and intersections are how you build complex types from simple ones. A union (A | B) means "either A or B". An intersection (A & B) means "both A and B at once". They are the algebra of types — and unions in particular are the single most important modeling tool in all of TypeScript.

1. Union types — "one of these"

unions.tstypescript 
type ID = string | number;          // either a string or a number
let userId: ID = 42;
userId = "abc-123";                 // both fine

// A union of literals is a precise, closed set of values:
type Size = "sm" | "md" | "lg";
function setSize(size: Size) { /* ... */ }
setSize("md");                      // ✅
// setSize("medium");               // ❌ not assignable

// On a union, you can only access members common to ALL branches:
function format(value: string | number) {
  // value.toUpperCase(); // ❌ number has no toUpperCase
  return value.toString(); // ✅ both string and number have toString
}
The safety rule: on a union value, TypeScript only lets you use what's valid for every possibility. To access branch-specific members, you must first narrow the union (next lesson). This is what makes unions safe rather than scary.

2. Intersection types — "all of these"

intersections.tstypescript 
type WithId = { id: string };
type WithTimestamps = { createdAt: string; updatedAt: string };

// An entity has an id AND timestamps:
type Entity = WithId & WithTimestamps;
const post: Entity = {
  id: "p1",
  createdAt: "2026-01-01",
  updatedAt: "2026-01-02",
};

// Common pattern: compose reusable "mixin" types.
type Serializable = { toJSON(): string };
type Loggable = { log(): void };
type Service = Serializable & Loggable; // must implement BOTH
Intersections build up bigger object types from small, reusable pieces — a clean way to share common fields (ids, timestamps, audit info) across many entities without repetition.
🧠
Concept · The counter-intuitive part

For objects, intersection & produces a type with more fields (more specific), while union | produces a type you can do less with (you must handle every case). "And" narrows what's valid; "or" widens it. Sit with that — it clicks with practice.

3. Discriminated unions (the crown jewel)

Add a shared literal "tag" field to each member of a union and you get a discriminated union — the most powerful everyday pattern in TypeScript. It lets the compiler know exactly which shape you have once you check the tag. We met it in 01-01; here's the mechanism.

discriminated.tstypescript 
type Shape =
  | { kind: "circle"; radius: number }
  | { kind: "rect"; width: number; height: number };

function area(shape: Shape): number {
  // Checking the "kind" tag narrows the type in each branch:
  switch (shape.kind) {
    case "circle":
      return Math.PI * shape.radius ** 2;   // shape is the circle variant here
    case "rect":
      return shape.width * shape.height;    // shape is the rect variant here
  }
}

console.log(area({ kind: "circle", radius: 2 }));      // ~12.57
console.log(area({ kind: "rect", width: 3, height: 4 })); // 12
This is the pattern behind everything robust — API responses, UI state machines, Redux actions, parser results. The shared kind (or type/status) field is the "discriminant"; checking it unlocks the branch-specific fields safely. We push this to exhaustive, bullet-proof extremes in Part 2.
📝
Exercise · An API result type

Model type Result<T> = { ok: true; value: T } | { ok: false; error: string }. Write function unwrap<T>(r: Result<T>): T that returns the value when ok is true and throws the error otherwise. Notice how checking r.ok lets you safely access r.value or r.error.

🎓 Key takeaways

  • Union A | B = "either"; you may only use members common to all branches until you narrow.
  • Intersection A & B = "both"; great for composing object shapes from reusable parts.
  • For objects: & adds fields (more specific), | demands handling every case.
  • Discriminated unions (a shared literal tag) are the #1 pattern for safe, expressive modeling.
  • Checking the discriminant narrows the type so branch-specific fields become accessible.
