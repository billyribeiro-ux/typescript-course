Git Workflows, Conventional Commits & Releases

🛠️ Collaboration ⏱️ ~28 min 🌿 Team practices

You learned Git basics in Part 0. Now we cover how teams use it: feature-branch workflows, pull requests and code review, the Conventional Commits standard that powers automated changelogs and versioning, and how releases happen. These practices are how professional teams ship dozens of changes a day without chaos.

1. The feature-branch / PR workflow

terminal
git switch -c feat/user-profile   # branch off main
# ...commit your work in small, logical commits...
git push -u origin feat/user-profile
# Open a Pull Request on GitHub. CI runs. A teammate reviews.
# Address feedback, then SQUASH-MERGE into main.
git switch main && git pull       # sync up
🧩
Concept · main is always shippable

The golden rule of "trunk-based" development: the main branch is always deployable. All work happens on short-lived feature branches, gets reviewed via a Pull Request, passes CI, and merges back. Branch protection rules enforce "no direct pushes to main; reviews + green CI required".

2. Conventional Commits

A simple, structured commit-message format that machines can parse to auto-generate changelogs and determine version bumps. The format is type(scope): description.

commit messages
feat(auth): add password reset flow         → MINOR bump
fix(cart): prevent negative quantities       → PATCH bump
docs(readme): update setup steps             → no release
refactor(api): extract request builder       → no release
test(utils): cover edge cases                → no release
feat(api)!: rename user endpoint             → MAJOR bump (! = breaking)
The common types: feat (new feature), fix (bug), docs, refactor, test, chore, perf, ci. A ! or a BREAKING CHANGE: footer signals a major version bump. This maps directly onto SemVer (lesson 03-01).

3. Automated versioning & changelogs

Tools read your conventional commits and do the release work for you. In the JS ecosystem, Changesets is the monorepo-friendly favourite; semantic-release fully automates from commits.

terminal (Changesets)
pnpm changeset             # describe your change + pick bump level
pnpm changeset version     # apply bumps + update CHANGELOG.md
pnpm changeset publish     # publish updated packages to npm
⚡
Pro-tip · Git hooks enforce quality

Tools like husky + lint-staged run checks automatically on git commit — formatting and linting only the staged files, and validating the commit message format. Bad commits never even enter history. Combined with CI (next lesson), quality is enforced at multiple gates.

4. Useful recovery commands

terminal
git stash                  # shelve changes temporarily
git restore --staged file   # unstage
git revert <hash>           # undo a commit with a NEW commit (safe)
git rebase main            # replay your branch on latest main
git reflog                 # your safety net — find "lost" commits
⚠️
Gotcha · Never force-push shared branches

git push --force rewrites history and can destroy teammates' work on a shared branch. If you must, use --force-with-lease (which refuses if someone else pushed). On main and shared branches: never force-push. On your own un-merged feature branch: it's usually fine.

📝
Exercise · A full PR cycle

On a practice repo, create a feat/ branch, make two conventional commits, push, and open a PR. Add a .changeset describing the change. Then practise git revert on a commit and observe that history is preserved (vs reset, which rewrites it).

🎓 Key takeaways

  • Feature branches + PRs + review + green CI, with main always shippable (trunk-based).
  • Conventional Commits (feat/fix/!) map to SemVer and power automation.
  • Changesets/semantic-release auto-generate changelogs and version bumps from commits.
  • husky + lint-staged enforce formatting/linting/commit format before code enters history.
  • Prefer revert (safe) over history rewriting; never force-push shared branches.
