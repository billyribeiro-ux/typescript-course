Monorepos with Turborepo

🛠️ Tooling ⏱️ ~28 min 🏎️ Build orchestration

pnpm workspaces let many packages live together; Turborepo makes building them fast and correct. It understands the dependency graph between your packages, runs tasks in the right order, runs them in parallel where possible, and — crucially — caches results so unchanged work is never repeated. This is how companies with hundreds of packages keep their builds fast.

1. The problem Turborepo solves

In a monorepo, pnpm -r build rebuilds everything, every time — even packages that didn't change. As the repo grows, this becomes painfully slow. Turborepo adds an intelligent task runner with a content-addressed cache: if a package's inputs haven't changed, its previous output is restored instantly.

terminal
pnpm add -D turbo -w     # add to the workspace root
turbo build             # build all packages, in graph order, cached
turbo build             # run again →
• Packages in scope: ui, utils, web
• Running build in 3 packages
  ✓ utils:build (cache hit, replaying logs)  0ms
  ✓ ui:build    (cache hit)                  0ms
  ✓ web:build   (cache hit)                  0ms
 Time: 120ms  >>> FULL TURBO
🧩
Concept · The task graph

If web depends on ui, then ui:build must finish before web:build starts. Turborepo reads your workspace graph and orders tasks automatically, parallelising independent ones across all CPU cores. You declare relationships, not order.

2. Configuring the pipeline

turbo.jsonjson 
{
  "$schema": "https://turbo.build/schema.json",
  "tasks": {
    "build": {
      "dependsOn": ["^build"],          // ^ = build my dependencies first
      "inputs": ["src/**", "tsconfig.json"],
      "outputs": ["dist/**"]            // what to cache
    },
    "test": {
      "dependsOn": ["build"]
    },
    "lint": {},
    "dev": {
      "cache": false,                   // never cache a long-running dev server
      "persistent": true
    }
  }
}
The two key ideas: "dependsOn": ["^build"] means "before building me, build everything I depend on" (the ^ points up the dependency graph). outputs tells Turbo what files to cache. Change one file in utils and only utils and its dependents rebuild — everything else is a cache hit.

3. Why caching is transformative

  • Local cache: re-running a task you've already run is instant.
  • Remote cache: teams (and CI) share a cache, so if a teammate already built a commit, your machine downloads the result instead of rebuilding. CI that took 20 minutes can drop to 2.
  • Correctness: the cache key is a hash of all inputs (source, deps, config, env), so a cache hit is guaranteed to equal a fresh build. Speed without risk.
✨
2026 context · Nx and the alternatives

Turborepo (by Vercel) is the lightweight, config-light choice we use. Nx is a heavier, more feature-rich alternative popular in large enterprises (code generators, dependency graph visualisation, plugins). Both solve the same core problem: fast, cached, ordered task running across a monorepo. The concepts transfer.

Exercise · Watch the cache work

In your workspace from 03-01, add Turborepo and a turbo.json with a cached build task. Run turbo build twice and observe the second run hit the cache. Then change one source file and run again — note only the affected packages rebuild. That's the whole value proposition, felt directly.

🎓 Key takeaways

  • Turborepo orchestrates monorepo tasks: correct order, parallelism, and caching.
  • "dependsOn": ["^build"] builds a package's dependencies before the package itself.
  • Content-hash caching skips unchanged work; a cache hit is guaranteed equal to a fresh build.
  • Remote caching shares results across the team and CI — minutes become seconds.
  • Nx is the heavier enterprise alternative; the concepts are the same.
