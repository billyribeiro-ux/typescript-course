CI/CD with GitHub Actions

🛠️ Automation ⏱️ ~30 min 🤖 Continuous integration

CI/CD — Continuous Integration / Continuous Deployment — means every push is automatically built, type-checked, linted, and tested, and (when ready) deployed. GitHub Actions is the most common tool: you describe a workflow in YAML, and GitHub runs it on every push or pull request. This is the automated safety net that lets teams move fast without breaking things.

1. A complete CI workflow

.github/workflows/ci.ymlyaml 
name: CI

on:
  push:
    branches: [main]
  pull_request:            # run on every PR

jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
        with: { version: 10 }
      - uses: actions/setup-node@v4
        with:
          node-version: 24
          cache: pnpm          # cache deps for speed
      - run: pnpm install --frozen-lockfile
      - run: pnpm tsc --noEmit  # types
      - run: pnpm lint          # correctness
      - run: pnpm prettier --check .  # formatting
      - run: pnpm test          # unit tests
      - run: pnpm build         # build must succeed
Read it top-to-bottom: on every push to main and every PR, spin up a fresh Ubuntu machine, install Node 24 + pnpm, install dependencies from the locked versions (--frozen-lockfile ensures reproducibility), then run the same quality gate you run locally. If any step fails, the PR is blocked. This is your check script (03-04), enforced on every change.

2. Key concepts

TermMeaning
WorkflowA YAML file describing automation, triggered by events.
Event (on)What triggers it: push, pull_request, schedule, manual.
JobA set of steps running on one fresh machine; jobs run in parallel by default.
StepA single command (run) or reusable action (uses).
RunnerThe machine (Ubuntu/macOS/Windows) executing a job.

3. Matrix builds & deployment

matrix + deployyaml 
jobs:
  test:
    strategy:
      matrix:
        node: [22, 24]      # run the SAME job across multiple Node versions
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      # ...test on each node version...

  deploy:
    needs: test             # only deploy if tests passed
    if: github.ref == 'refs/heads/main'   # only on main
    runs-on: ubuntu-latest
    steps:
      - run: echo "Deploying..."   # e.g. vercel deploy, or push a Docker image
        env:
          DEPLOY_TOKEN: ${{ secrets.DEPLOY_TOKEN }}  # secrets, never hardcoded
Two professional patterns: a matrix runs the same checks across several Node versions (catching version-specific bugs), and a deploy job that needs the test job ensures you only ship green code. Secrets live in GitHub's encrypted store and are injected as env vars — never committed to the repo.

Exercise · Add CI to a project

Add the ci.yml above to your P02 monorepo (or any repo with tests). Push a branch and open a PR — watch the checks run on GitHub. Then intentionally break a test and push; confirm the PR goes red and is blocked. You've built a real safety net.

🎓 Key takeaways

  • CI runs your quality gate (types, lint, format, test, build) automatically on every push/PR.
  • A workflow (YAML) has jobs (parallel machines) made of steps (run/uses).
  • Use --frozen-lockfile + dependency caching for reproducible, fast installs.
  • Matrix builds test across versions; needs + if gate deployment on green tests + the right branch.
  • Secrets live in GitHub's encrypted store — never in the repo.
