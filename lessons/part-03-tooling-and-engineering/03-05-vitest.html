Testing with Vitest

🛠️ Tooling ⏱️ ~32 min ✅ Confidence

Tests are how you change code without fear. Vitest is the modern test runner — fast, Vite-powered, with a Jest-compatible API and first-class TypeScript support. You already used it in Projects P01 and P02; now we cover it properly: structure, matchers, mocking, async tests, coverage, and the type-level testing you saw in P02.

1. Anatomy of a test

math.test.tstypescript 
import { describe, it, expect } from "vitest";
import { add } from "./math.js";

describe("add", () => {                 // groups related tests
  it("sums two positive numbers", () => {
    expect(add(2, 3)).toBe(5);          // assertion
  });

  it("handles negatives", () => {
    expect(add(-1, -1)).toBe(-2);
  });

  it.each([                             // table-driven tests
    [1, 1, 2],
    [0, 5, 5],
    [-2, 2, 0],
  ])("add(%i, %i) = %i", (a, b, expected) => {
    expect(add(a, b)).toBe(expected);
  });
});
The structure: describe groups, it (or test) defines a case, expect(...).matcher(...) asserts. it.each runs the same test over a table of inputs — perfect for covering many cases concisely. This is exactly the shape of P01's and P02's test suites.

2. Matchers you'll actually use

matchers.test.tstypescript 
expect(value).toBe(5);                 // strict === (primitives)
expect(obj).toEqual({ a: 1 });         // deep equality (objects/arrays)
expect(list).toContain("x");
expect(list).toHaveLength(3);
expect(value).toBeTruthy();            // / toBeNull / toBeUndefined
expect(value).toBeGreaterThan(10);
expect(str).toMatch(/error/i);         // regex
expect(() => risky()).toThrow(/invalid/); // function throws
await expect(promise).resolves.toBe(42);  // async resolution
await expect(promise).rejects.toThrow();  // async rejection
The big one: toBe vs toEqual. toBe is reference/ primitive equality (===); toEqual recursively compares structure. Use toBe for numbers/strings/booleans, toEqual for objects and arrays. Mixing them up is the #1 beginner test bug.

3. Mocking & spies

mocking.test.tstypescript 
import { describe, it, expect, vi, beforeEach } from "vitest";

// A spy/mock function tracks how it was called:
const onSave = vi.fn();
onSave("a");
expect(onSave).toHaveBeenCalledWith("a");
expect(onSave).toHaveBeenCalledTimes(1);

// Mock a whole module (e.g. avoid real network in tests):
vi.mock("./api.js", () => ({
  fetchUser: vi.fn().mockResolvedValue({ id: 1, name: "Ada" }),
}));

// Control time deterministically:
beforeEach(() => vi.useFakeTimers());
// ... vi.advanceTimersByTime(1000) ...
Mock the edges, test the core. Mock network calls, timers, and external services so tests are fast and deterministic — then test your logic for real. This is why P01/P02 put logic in pure functions: pure code needs almost no mocking, which is the secret to a fast, reliable suite.

4. Coverage & type testing

terminal
pnpm vitest                  # watch mode (re-runs on save)
pnpm vitest run              # single run (CI)
pnpm vitest run --coverage   # % of code exercised by tests
pnpm vitest --typecheck      # run *.test-d.ts TYPE-level tests
📊
Note · Coverage is a tool, not a target

Coverage shows which lines ran during tests. Useful for finding untested code, but 100% coverage doesn't mean bug-free — you can execute a line without asserting it's correct. Aim to test behaviour and edge cases, not to chase a number. And remember --typecheck for the expectTypeOf assertions you wrote in P02.

🎓 Key takeaways

  • Vitest: describe/it/expect, with it.each for table-driven tests.
  • toBe for primitives/references; toEqual for deep object/array equality.
  • Use vi.fn()/vi.mock() to mock the edges (network, timers); test pure logic for real.
  • --coverage finds untested code; --typecheck runs type-level tests.
  • Pure functions (P01/P02 style) make for fast, mock-free, reliable suites.
