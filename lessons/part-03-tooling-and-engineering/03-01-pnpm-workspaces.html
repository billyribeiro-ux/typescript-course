Package Managers & pnpm Workspaces

🛠️ Tooling ⏱️ ~28 min 📦 Dependency mastery

Every project you build stands on a tower of open-source packages. The package manager installs and organises them, and pnpm — the 2026 professional standard — does it faster and more correctly than the alternatives. Understanding how dependencies, versions, and lockfiles work is the difference between "works on my machine" and reproducible, reliable builds.

1. What a package manager really does

When you pnpm add react, the manager resolves the full dependency tree, downloads the packages, records exact versions in a lockfile, and links them into node_modules. The lockfile is what makes installs reproducible — everyone gets the exact same versions.

terminal
pnpm add react react-dom        # runtime dependency
pnpm add -D vitest typescript    # dev-only dependency (-D)
pnpm add -E zod                  # pin EXACT version (no ^ range)
pnpm install                     # install everything from the lockfile
pnpm up --latest                  # upgrade to newest versions
pnpm why react                   # explain WHY a package is installed
🧩
Concept · dependencies vs devDependencies

dependencies ship with your app at runtime (React, Zod). devDependencies are only needed to build/test (TypeScript, Vitest, ESLint). Getting this split right keeps production installs lean. UI libraries you import = dependency; tools you run = devDependency.

Pro-tip · pnpm's strictness is a feature

pnpm uses a non-flat node_modules, so you can't accidentally import a package you didn't declare (a "phantom dependency"). This catches a real class of bugs where code works locally but breaks when a transitive dependency changes. Strict by default = fewer 2am surprises.

3. Semantic versioning

package.json (versions)json 
{
  "dependencies": {
    "react": "^19.1.0",     // ^ = compatible: >=19.1.0 <20.0.0 (minor+patch ok)
    "zod": "~3.24.1",       // ~ = patch only: >=3.24.1 <3.25.0
    "left-pad": "1.3.0"     // exact: only 1.3.0
  }
}
// SemVer is MAJOR.MINOR.PATCH:
//   MAJOR = breaking changes
//   MINOR = new features, backward-compatible
//   PATCH = bug fixes, backward-compatible
The lockfile is the source of truth. The ranges (^, ~) in package.json say what's allowed; the pnpm-lock.yaml records what's actually installed. Always commit your lockfile — it's what guarantees your teammate and your CI server build the identical tree.

4. Workspaces: many packages, one repo

A workspace (monorepo) holds multiple related packages that can depend on each other, sharing one install and one lockfile. This is how teams manage a design system + several apps together.

pnpm-workspace.yamlyaml 
packages:
  - "apps/*"        # your applications
  - "packages/*"    # shared libraries (ui, config, utils)
terminal
pnpm --filter web add @myorg/ui     # add a workspace pkg as a dep
pnpm --filter web dev               # run a script in one package
pnpm -r build                       # run "build" in EVERY package
The workspace:* protocol lets apps/web depend on packages/ui by its name, resolved to the local code — no publishing needed during development. We build a real workspace in lesson 03-10.
📝
Exercise · Set up a workspace

Create a folder with a pnpm-workspace.yaml declaring packages/*. Add two packages — packages/utils (exports a function) and packages/app (depends on utils via "@you/utils": "workspace:*"). Run pnpm install and import the function across packages. You've built your first monorepo.

🎓 Key takeaways

  • The package manager resolves, installs, and locks dependency versions for reproducible builds — always commit the lockfile.
  • pnpm is fastest, disk-efficient, and strict (no phantom dependencies) — the 2026 standard.
  • Split dependencies (runtime) from devDependencies (build/test tools).
  • SemVer: ^ allows minor+patch, ~ patch only, exact pins one version.
  • Workspaces manage multiple inter-dependent packages with one install — the basis of monorepos.
