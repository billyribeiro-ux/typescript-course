Type-Safe Routing with TanStack Router

🧩 Ecosystem ⏱️ ~28 min 🔒 Fully typed URLs

TanStack Router brings the type-safety obsession of Parts 1–2 to navigation. Every route path, every URL param, and every search-query parameter is fully typed and validated — a typo in a link or a missing param is a compile error. For a TypeScript-first team, this is a game-changer. Here's why it's winning mindshare in 2026.

1. The problem with stringly-typed routing

In most routers, navigate("/prodcuts/" + id) (note the typo) compiles fine and breaks at runtime. Params are string | undefined with no guarantee they exist. Search params are an untyped free-for-all. TanStack Router eliminates all of this by generating types from your route tree.

2. Type-safe routes & links

routes.tsxtsx 
import { createFileRoute } from "@tanstack/react-router";
import { z } from "zod";

// A route with a typed param AND validated search params:
export const Route = createFileRoute("/products/$productId")({
  // Validate & type the ?page=&sort= search params with a schema:
  validateSearch: z.object({
    page: z.number().catch(1),
    sort: z.enum(["price", "name"]).catch("name"),
  }),
  loader: ({ params }) => fetchProduct(params.productId), // params.productId: string
  component: ProductPage,
});

function ProductPage() {
  const { productId } = Route.useParams();   // typed as string
  const { page, sort } = Route.useSearch();  // page: number, sort: "price"|"name"
  return <h1>Product {productId} — page {page}, sorted by {sort}</h1>;
}
Search params are first-class and validated. The validateSearch schema (using Zod — lesson 06-09, and your P02!) parses ?page=2&sort=price into typed values with fallbacks. Route.useParams() and Route.useSearch() are fully typed to this route — no string | undefined guessing.

3. Links that can't be wrong

typed-links.tsxtsx 
import { Link } from "@tanstack/react-router";

<Link
  to="/products/$productId"        // ✅ autocompleted, checked against the route tree
  params={{ productId: "42" }}     // ✅ required params enforced by types
  search={{ page: 2, sort: "price" }} // ✅ typed search params
>
  View product
</Link>;

// <Link to="/prodcuts/$id" />     // ❌ compile error: no such route
// <Link to="/products/$productId" /> // ❌ compile error: missing params
The whole navigation surface is type-checked. A wrong path, a missing param, or a malformed search object won't compile. Refactor a route and every broken link lights up red. This is the same "make illegal states unrepresentable" philosophy from Part 2, applied to your app's URLs.
⚡
Pro-tip · Pairs perfectly with TanStack Query

TanStack Router's loaders integrate with TanStack Query (next lesson) for caching and preloading, and it supports first-class search-param state (great for filters/pagination you want in the URL). The whole TanStack suite is built by the same team to compose. TanStack Start extends it into a full SSR framework (Part 7 alternative to Next.js).

Exercise · Typed search filters

Build a /search route whose search params (q: string, page: number, category: enum) are validated with a Zod schema. Render a filter UI that updates the URL via typed <Link>s / navigate, and read them back fully typed. Confirm a wrong param name is a compile error.

🎓 Key takeaways

  • TanStack Router makes paths, params, and search params fully type-safe — typos and missing params are compile errors.
  • validateSearch (with Zod) parses and types URL search params with fallbacks.
  • Route.useParams()/useSearch() are typed to the specific route — no undefined guessing.
  • Typed <Link>s enforce correct routes/params at compile time and survive refactors.
  • Composes with TanStack Query and TanStack Start for caching and SSR.
