Project P05 — The Redux Enterprise Admin

🏗️ Build ⏱️ ~90 min ✅ 14 tests

An enterprise-style users admin built with Redux Toolkit — the structured, battle-tested state pattern you'll meet at large companies. We use normalized entities, typed slices, memoized selectors, and a test setup that proves both the pure logic and the UI. The project lives in projects/p05-redux-enterprise-admin/ with 14 passing tests.

1. Normalized entities with createEntityAdapter

usersSlice.ts (excerpt)typescript 
const usersAdapter = createEntityAdapter<User>({
  sortComparer: (a, b) => a.name.localeCompare(b.name),
});

const usersSlice = createSlice({
  name: "users",
  initialState: usersAdapter.getInitialState({}, seedUsers),
  reducers: {
    addUser: {
      reducer: usersAdapter.addOne,
      prepare: (input: { name: string; email: string; role: Role }) => ({
        payload: { id: nanoid(), active: true, ...input } satisfies User,
      }),
    },
    setRole: (state, action: PayloadAction<{ id: string; role: Role }>) => {
      const user = state.entities[action.payload.id];
      if (user) user.role = action.payload.role; // Immer "mutation"
    },
  },
});
createEntityAdapter gives you normalized state for free — entities keyed by id, sorted selectors, and CRUD reducers (addOne/removeOne/…). The prepare callback generates the id with nanoid before the reducer runs, and satisfies User (02-10!) checks the payload shape. This is the same normalized shape as the P04 Kanban board — the professional default.

2. Store, derived types & memoized selectors

store.ts (excerpt)typescript 
export const store = configureStore({
  reducer: { users: usersReducer, filters: filtersReducer, auth: authReducer },
});
export type RootState = ReturnType<typeof store.getState>; // derived (02-04)
export type AppDispatch = typeof store.dispatch;

export const useAppSelector = useSelector.withTypes<RootState>();
export const useAppDispatch = useDispatch.withTypes<AppDispatch>();

// Memoized derived data — only recomputes when inputs change:
export const selectVisibleUsers = createSelector(
  [selectAllUsers, (s: RootState) => s.filters],
  (users, filters) => users.filter((u) =>
    (filters.role === "all" || u.role === filters.role) &&
    (u.name + u.email).toLowerCase().includes(filters.search.trim().toLowerCase())),
);
Types are derived from the store (lesson 02-04), so they never drift. createSelector memoizes derived data — selectVisibleUsers only recomputes when the users or filters actually change, not on every render. Components read it with the typed useAppSelector. This is the canonical RTK architecture.

3. Testing Redux: pure logic + UI

tests (excerpt)tsx 
// Pure: dispatch actions to an isolated store, assert on selectors:
const store = makeStore();
store.dispatch(setRoleFilter("admin"));
expect(selectVisibleUsers(store.getState())).toHaveLength(1);

// UI: render inside a fresh <Provider> (preloaded state supported):
renderWithStore(<UsersTable />, { filters: { search: "", role: "admin" } });
expect(screen.getAllByTestId("user-row")).toHaveLength(1);

// Interaction updates the real store:
await user.selectOptions(screen.getByLabelText("Role for Linus Torvalds"), "admin");
expect(store.getState().users.entities.u2?.role).toBe("admin");
A makeStore() factory is the key to clean Redux tests. Each test gets a fresh, isolated store (optionally preloaded with state), so there's no shared-state pollution. Pure slice/selector tests need no rendering; component tests render inside a <Provider> with the same factory. Because reducers are pure, they're as easy to test as P01/P02.
