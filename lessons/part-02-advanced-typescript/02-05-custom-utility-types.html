Building Your Own Utility Types

🧠 Advanced ⏱️ ~36 min 🛠️ Type engineering

Now you compose everything — conditional types, infer, mapped types, key remapping — into your own production-grade utilities. We'll also learn the type-testing discipline that principal engineers use to keep complex types correct: assertion helpers that turn type bugs into compile errors. This is exactly how the P02 validator's types were verified.

1. The type-testing toolkit

Before building, learn to test. These tiny helpers let you assert that two types are equal at compile time. If an assertion fails, you get a red error — your type "unit tests".

type-tests.tstypescript 
// The canonical strict equality check (handles `any` correctly):
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends (<T>() => T extends B ? 1 : 2)
    ? true : false;

// Assert a type is exactly `true` — fails to compile otherwise:
type Expect<T extends true> = T;

// Usage — these are your tests:
type _t1 = Expect<Equal<Pick<{ a: 1; b: 2 }, "a">, { a: 1 }>>; // ✅ passes
// type _bad = Expect<Equal<1, 2>>; // ❌ compile error: 1 is not 2

// A simpler (looser) variant when you just need assignability:
type ExpectAssignable<T, U extends T> = U;
This Equal trick is famous (it uses function-type variance to detect exact equality, distinguishing any from unknown). The Expect<Equal<...>> pattern is how libraries like the validator you built guarantee their inference stays correct as code changes. We ran exactly these assertions to verify Part 2's code.

2. Building real utilities

my-utils.tstypescript 
// Prettify — flatten intersections into one clean object (great for tooltips):
type Prettify<T> = { [K in keyof T]: T[K] } & {};

// PartialBy / RequiredBy — make SPECIFIC keys optional/required:
type PartialBy<T, K extends keyof T> = Prettify<Omit<T, K> & Partial<Pick<T, K>>>;
type RequiredBy<T, K extends keyof T> = Prettify<Omit<T, K> & Required<Pick<T, K>>>;

// ValueOf — the union of a type's value types:
type ValueOf<T> = T[keyof T];

// Entries — model Object.entries() at the type level:
type Entries<T> = { [K in keyof T]: [K, T[K]] }[keyof T];

interface Post { id: number; title: string; draft: boolean }
type DraftInput = PartialBy<Post, "id">;  // id optional, rest required
type PostValues = ValueOf<Post>;          // number | string | boolean
type PostEntries = Entries<Post>;
// ["id", number] | ["title", string] | ["draft", boolean]
These four are workhorses. Prettify alone dramatically improves the developer experience by collapsing ugly intersection tooltips into clean object types — the P02 library uses it. PartialBy models real create/update DTOs. ValueOf and Entries bridge to runtime Object methods.

3. A genuinely hard one: DeepPartial

deep-partial.tstypescript 
// Recurse into nested objects, but DON'T break arrays or functions.
type DeepPartial<T> = T extends (...args: any[]) => any
  ? T
  : T extends ReadonlyArray<infer U>
  ? ReadonlyArray<DeepPartial<U>>
  : T extends object
  ? { [K in keyof T]?: DeepPartial<T[K]> }
  : T;

interface Settings {
  theme: { color: string; mode: "light" | "dark" };
  plugins: { name: string; enabled: boolean }[];
}
type PatchSettings = DeepPartial<Settings>;
const patch: PatchSettings = { theme: { mode: "dark" } }; // ✅ deeply optional
Order matters in conditional chains: we test for functions and arrays before the generic object branch, because functions and arrays are also objects. Get the order wrong and you'll mangle them. This is the kind of careful, ordered conditional logic that separates robust utilities from subtly-broken ones.
⚠️
Gotcha · Always test edge cases

Custom utilities break on edge cases: any, never, unions, optional properties, arrays, functions, readonly. Write Expect<Equal<...>> assertions for each. A utility that works on { a: number } but mangles string[] is a landmine in a shared codebase.

📝
Exercise · Build and test Mutable + Replace

1) Mutable<T> — strip all readonly modifiers. 2) Replace<T, K extends keyof T, V> — change the type of key K to V (hint: Omit<T, K> & Record<K, V>, then Prettify). Write at least two Expect<Equal<...>> assertions for each.

🎓 Key takeaways

  • Test types with Equal<A,B> + Expect<T extends true> — type bugs become compile errors.
  • Prettify, PartialBy/RequiredBy, ValueOf, Entries are everyday custom utilities.
  • Recursive utilities (DeepPartial) must order conditional branches carefully (functions/arrays before objects).
  • Always test edge cases: any, never, unions, arrays, functions, optional, readonly.
  • This is the exact discipline used to verify the P02 validator's inference.
