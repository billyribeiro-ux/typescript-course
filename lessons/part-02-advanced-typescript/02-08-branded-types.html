Branded & Nominal Types

🧠 Advanced ⏱️ ~30 min 🏷️ Type identity

TypeScript is structurally typed: two types are compatible if their shapes match, regardless of name. Usually that's a feature — but sometimes you need two same-shaped types to be incompatible: a UserId must never be passed where a PostId is expected, even though both are strings. Branded types add nominal (name-based) safety on top of the structural system. This is a hallmark of robust, large-scale codebases.

1. The structural-typing problem

the-problem.tstypescript 
type UserId = string;
type PostId = string;

function getUser(id: UserId) { /* ... */ }

const postId: PostId = "post_123";
getUser(postId); // 😱 compiles fine — both are just `string`!

// Plain type aliases give NO protection. A swapped id is a classic,
// expensive production bug (fetching the wrong record, leaking data).
Type aliases are not new types — UserId and PostId are both literally string, so the compiler sees no difference. Passing a post id as a user id is exactly the kind of subtle bug that causes security incidents. We need real nominal distinction.

2. Branding for nominal safety

branding.tstypescript 
// A reusable Brand helper. The & { __brand } is a phantom tag — it exists
// only at the type level (there's no real __brand property at runtime).
declare const __brand: unique symbol;
type Brand<T, B> = T & { readonly [__brand]: B };

type UserId = Brand<string, "UserId">;
type PostId = Brand<string, "PostId">;

// "Smart constructors" are the only way to mint a branded value:
function UserId(raw: string): UserId { return raw as UserId; }
function PostId(raw: string): PostId { return raw as PostId; }

function getUser(id: UserId) { /* ... */ }

getUser(UserId("u_1"));        // ✅
// getUser(PostId("p_1"));     // ❌ PostId is not assignable to UserId
// getUser("u_1");             // ❌ raw string is not a UserId either
How it works: intersecting with a phantom { [__brand]: B } makes UserId and PostId structurally distinct, even though both are strings at runtime. The only way to create one is through its constructor, which is the single place validation lives. Now the compiler enforces that ids never get crossed.

3. Branding for validated values

validated.tstypescript 
declare const __brand: unique symbol;
type Brand<T, B> = T & { readonly [__brand]: B };

type Email = Brand<string, "Email">;
type PositiveInt = Brand<number, "PositiveInt">;

// The constructor VALIDATES, then brands. Past this point, the type itself
// guarantees the value was checked — you never re-validate downstream.
function Email(raw: string): Email {
  if (!/^[^@\s]+@[^@\s]+\.[^@\s]+$/.test(raw)) throw new Error("Invalid email");
  return raw as Email;
}
function PositiveInt(n: number): PositiveInt {
  if (!Number.isInteger(n) || n <= 0) throw new Error("Must be positive int");
  return n as PositiveInt;
}

// A function can now DEMAND a validated email at the type level:
function sendWelcome(to: Email) { /* guaranteed valid — no checks needed */ }
sendWelcome(Email("a@b.com")); // ✅
// sendWelcome("a@b.com");     // ❌ must go through the validator
This is "parse, don't validate" elevated. A branded Email is a proof that validation happened. Functions accepting Email can't be called with an unchecked string. Validation moves to the system's edge (the constructor), and the type system carries the guarantee everywhere else — eliminating defensive re-checking and "is this validated yet?" uncertainty.
🔗
Note · This is how Zod's `.brand()` works

Real validation libraries (Zod, and you could add it to your P02 validator) offer a .brand<"Email">() method that produces exactly these phantom-branded types — so a parsed value is statically distinguishable from an unparsed one. You now understand the mechanism completely.

🎓 Key takeaways

  • TypeScript is structural — same-shaped types are interchangeable, which is sometimes unsafe.
  • Branded types (T & { [__brand]: B }) add nominal distinction using a phantom tag.
  • Smart constructors are the only way to mint branded values — the single place validation lives.
  • A branded type is a proof of validation: functions can demand checked values, eliminating defensive re-checks.
  • This underlies Zod's .brand() and is a hallmark of large, safety-critical codebases.
