Discriminated Unions & Exhaustiveness

🧠 Advanced · pivotal ⏱️ ~36 min 🚦 Modeling states

This is the most important applied pattern in all of TypeScript: using discriminated unions to make illegal states unrepresentable. It's how you model async data, UI state machines, API responses, and Redux actions so that entire categories of bugs become compile errors. If you take one pattern from this course to your Meta/Google interview, make it this one.

1. From boolean soup to a clean state machine

states.tstypescript 
// ❌ "Boolean soup" — permits nonsense like isLoading && hasError && data.
interface BadState<T> {
  isLoading: boolean;
  data?: T;
  error?: string;
}

// ✅ Discriminated union — only the FOUR valid states can exist.
type RequestState<T> =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: T }
  | { status: "error"; error: string };

function render<T>(state: RequestState<T>): string {
  switch (state.status) {
    case "idle":    return "Start";
    case "loading": return "Spinner";
    case "success": return `Got ${JSON.stringify(state.data)}`; // data exists here
    case "error":   return `Error: ${state.error}`;             // error exists here
  }
}
The win: in BadState you can construct { isLoading: true, error: "x", data: {...} } — a meaningless state your UI must defend against. In RequestState, that's impossible to even write. The shared status literal (the "discriminant") lets the compiler narrow to the exact variant in each branch, so state.data is only reachable when it actually exists.

2. Bullet-proof exhaustiveness

exhaustive.tstypescript 
type Shape =
  | { kind: "circle"; r: number }
  | { kind: "square"; side: number }
  | { kind: "rect"; w: number; h: number };

function assertNever(value: never): never {
  throw new Error(`Unhandled case: ${JSON.stringify(value)}`);
}

function area(shape: Shape): number {
  switch (shape.kind) {
    case "circle": return Math.PI * shape.r ** 2;
    case "square": return shape.side ** 2;
    case "rect":   return shape.w * shape.h;
    default:       return assertNever(shape); // compile error if a case is missed
  }
}
// Add a "triangle" variant to Shape and `area` fails to compile until you
// handle it — the compiler becomes your checklist.
This is the professional pattern. assertNever in the default branch turns "I forgot to handle a case" from a silent runtime bug into a compile error. When you extend the union months later, every unhandled switch across the codebase lights up red. This is how large teams safely evolve shared types.

3. Real applications

applications.tstypescript 
// A Result type — type-safe errors without exceptions (Rust-style):
type Result<T, E = Error> =
  | { ok: true; value: T }
  | { ok: false; error: E };

function parseAge(input: string): Result<number, string> {
  const n = Number(input);
  return Number.isInteger(n) && n >= 0
    ? { ok: true, value: n }
    : { ok: false, error: "Not a valid age" };
}
const r = parseAge("42");
if (r.ok) console.log(r.value); else console.log(r.error);

// Redux-style actions — the discriminant is `type`:
type Action =
  | { type: "increment"; by: number }
  | { type: "reset" }
  | { type: "setName"; name: string };

function reducer(state: { count: number; name: string }, action: Action) {
  switch (action.type) {
    case "increment": return { ...state, count: state.count + action.by };
    case "reset":     return { ...state, count: 0 };
    case "setName":   return { ...state, name: action.name };
  }
}
You'll meet this everywhere ahead: useReducer (Part 4) and Redux Toolkit (Part 6) are built on discriminated-union actions. The Result type is how serious codebases handle expected failures without throwing. This single pattern is the backbone of reliable application state.
⚡
Pro-tip · Choose a consistent discriminant

Pick one discriminant name and stick to it across the codebase — type, kind, or status. Consistency lets you write generic helpers (like a typed event bus or a pattern-matcher) that work across all your unions. Mixing discriminant names is a smell.

Design a discriminated union Checkout with states: cart (has items), shipping (has address), payment (has a token), confirmed (has an order id). Write a summary(c: Checkout): string with an exhaustive switch + assertNever. Then add a "failed" state and watch the compiler demand you handle it.

🎓 Key takeaways

  • Discriminated unions make illegal states unrepresentable — model state machines, not boolean soup.
  • A shared literal discriminant (status/kind/type) lets the compiler narrow to the exact variant.
  • assertNever in default turns missed cases into compile errors — your future-proof checklist.
  • The Result<T,E> type handles expected failures without exceptions.
  • This pattern underpins useReducer, Redux actions, and reliable async UI state.
