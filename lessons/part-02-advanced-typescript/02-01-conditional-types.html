Conditional Types & infer

🧠 Advanced ⏱️ ~38 min 🔬 Type-level programming

Welcome to type-level programming — where types stop being static labels and become a computation the compiler runs. Conditional types are the if/else of this language-within-a-language, and infer is its pattern-matching const. Master these two and you can express almost anything about the shape of data. This is the foundation the entire rest of Part 2 builds on.

1. The conditional type

A conditional type has the form T extends U ? X : Y — "if T is assignable to U, the type is X, otherwise Y". It's a ternary that operates on types.

conditional.tstypescript 
type IsString<T> = T extends string ? true : false;

type A = IsString<"hello">; // true
type B = IsString<42>;      // false

// Conditional types shine when the parameter is generic — they compute per use:
type ToArray<T> = T extends unknown[] ? T : T[];
type C = ToArray<number>;   // number[]
type D = ToArray<string[]>; // string[] (already an array, left as-is)

// They power "smart" return types. This is the real-world payoff:
type ApiPath<T> = T extends "user" ? { id: number; name: string }
               : T extends "post" ? { id: number; title: string }
               : never;
type User = ApiPath<"user">; // { id: number; name: string }
The mental shift: extends here doesn't mean inheritance — it means "assignable to". T extends U asks "is every value of T also a value of U?" The whole expression resolves to one branch once T is known. Chaining them (as in ApiPath) builds a type-level lookup.

2. infer — pattern-matching inside a type

infer introduces a type variable inside the extends clause and lets the compiler solve for it. It's how you "pull a type out of" another type — the single most powerful tool in your type-level toolkit.

infer.tstypescript 
// "If T is an array of some element E, give me E":
type ElementOf<T> = T extends (infer E)[] ? E : never;
type E1 = ElementOf<string[]>;        // string
type E2 = ElementOf<number[][]>;      // number[]

// Unwrap a Promise — exactly how the built-in Awaited works:
type Unwrap<T> = T extends Promise<infer V> ? V : T;
type R = Unwrap<Promise<{ id: number }>>; // { id: number }

// Extract a function's return type (this IS the built-in ReturnType):
type MyReturnType<F> = F extends (...args: any[]) => infer R ? R : never;
function makeUser() { return { id: 1, name: "Ada" }; }
type MadeUser = MyReturnType<typeof makeUser>; // { id: number; name: string }

// Extract the FIRST parameter's type:
type FirstParam<F> = F extends (first: infer P, ...rest: any[]) => any ? P : never;
type P = FirstParam<(name: string, age: number) => void>; // string
This is the payoff from P02. Recall Infer<S> = S extends Schema<infer T> ? T : never — that's exactly this pattern, pulling the validated type out of a schema. infer says "I don't know what's here, but capture it and call it E/V/R". The compiler matches the structure and fills it in.

3. Distribution over unions (the subtle, crucial rule)

When a conditional type's checked type is a naked generic parameter and you pass a union, the conditional distributes — it applies to each member separately and unions the results. This is powerful, occasionally surprising, and you must understand it.

distribution.tstypescript 
type ToArray<T> = T extends unknown ? T[] : never;

// Distributes over the union: applies to string, then number, separately:
type Distributed = ToArray<string | number>; // string[] | number[]
//   NOT (string | number)[] !

// To STOP distribution, wrap both sides in a tuple ("[T] extends [U]"):
type ToArrayNoDist<T> = [T] extends [unknown] ? T[] : never;
type NotDistributed = ToArrayNoDist<string | number>; // (string | number)[]

// The built-in Exclude/Extract rely on distribution:
type MyExclude<T, U> = T extends U ? never : T;
type WithoutB = MyExclude<"a" | "b" | "c", "b">; // "a" | "c"
The rule: a "naked" type parameter (T extends ..., not [T] extends [...]) distributes across unions. Exclude exploits this to filter union members. When you don't want distribution, wrap in single-element tuples. Knowing exactly when distribution kicks in separates intermediate from expert.
⚠️
Gotcha · boolean is `true | false`

Because boolean is internally the union true | false, a distributing conditional over boolean runs twice. T extends true ? "y" : "n" applied to boolean yields "y" | "n", not a single branch. Watch for this in predicates.

4. A real utility: function-aware types

real-utility.tstypescript 
// Recursively unwrap nested Promises (Promise<Promise<T>> → T):
type DeepAwaited<T> = T extends Promise<infer V> ? DeepAwaited<V> : T;
type X = DeepAwaited<Promise<Promise<number>>>; // number

// Build a type for "the resolved data of an async function":
type AsyncReturn<F> =
  F extends (...args: any[]) => Promise<infer R> ? R : never;

async function fetchUser(id: number) {
  return { id, name: "Ada" };
}
type FetchedUser = AsyncReturn<typeof fetchUser>; // { id: number; name: string }
// This is how data-fetching libraries infer your response types for free.
Why this matters for React: TanStack Query, tRPC, and server-action frameworks use exactly these conditional-infer patterns to give you fully-typed data from a single function definition — no manual type annotations. You're learning the machinery behind the magic.

🎓 Key takeaways

  • Conditional types T extends U ? X : Y are the if/else of type-level programming (extends = "assignable to").
  • infer captures a type from within a structure — the basis of ReturnType, Awaited, and P02's Infer<S>.
  • Naked type params distribute over unions; wrap in [T] to prevent it.
  • Exclude/Extract are built on distribution; boolean distributes as true | false.
  • These patterns power the type inference in every modern data library — learn them deeply.
