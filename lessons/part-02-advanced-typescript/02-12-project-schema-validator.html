Project P02 — A Type-Safe Schema Validator (mini-Zod)

🏗️ Build ⏱️ ~90 min ✅ 14 runtime + 6 type tests

The grand finale of Part 2: build a real validation library where a single schema declaration is both the runtime validator and the source of the static type. This is "parse, don't validate" in full force, and it exercises every advanced concept you just learned. The complete, tested project lives in projects/p02-type-safe-schema-validator/.

🎯
The goal · one declaration, two outputs

From const User = v.object({ name: v.string(), age: v.number() }) we get BOTH a runtime User.parse(unknownData) that validates, AND a static type User = Infer<typeof User> equal to { name: string; age: number }. The schema is the single source of truth — types and validation can never drift.

1. The type-level engine

src/types.tstypescript 
// Pull the validated type out of a schema (02-01: conditional + infer):
export type Infer<S> = S extends Schema<infer T> ? T : never;

export type Prettify<T> = { [K in keyof T]: T[K] } & {};
export type ObjectShape = Record<string, Schema<unknown>>;

// 02-02: mapped types + key remapping to SPLIT required vs optional keys.
type OptionalKeys<S extends ObjectShape> = {
  [K in keyof S]: S[K] extends OptionalSchema<unknown> ? K : never;
}[keyof S];
type RequiredKeys<S extends ObjectShape> = Exclude<keyof S, OptionalKeys<S>>;

export type InferObject<S extends ObjectShape> = Prettify<
  { [K in RequiredKeys<S>]: Infer<S[K]> } & { [K in OptionalKeys<S>]?: Infer<S[K]> }
>;
Every Part 2 concept, applied: Infer uses conditional types + infer (02-01). InferObject uses mapped types with key remapping (02-02) and conditional types to route each key into the required or optional group — the exact technique from 02-02 — then Prettify (02-05) cleans the tooltip. This is the brain of the library.

2. The runtime engine + variance insight

src/schemas.ts (excerpt)typescript 
export abstract class Schema<Output> {
  protected abstract check(value: unknown, path: Path, issues: Issue[]): Output;

  // Type-erased to Check<unknown> ON PURPOSE: keeps Output out of any visible
  // contravariant position, so Schema<string> stays assignable to Schema<unknown>.
  protected refinements: ReadonlyArray<Check<unknown>> = [];

  parse(value: unknown): Output { /* run check + refinements, throw if issues */ }
  safeParse(value: unknown): SafeParseResult<Output> { /* discriminated union */ }
  optional(): OptionalSchema<Output> { return new OptionalSchema(this); }
}

export const v = {
  string: () => new StringSchema(),
  number: () => new NumberSchema(),
  // 02-10: a `const` type param keeps "admin" narrow, not widened to string:
  literal: <const L extends string | number | boolean>(value: L) => new LiteralSchema(value),
  object: <S extends ObjectShape>(shape: S) => new ObjectSchema(shape),
  union: <T extends readonly [Schema<unknown>, ...Schema<unknown>[]]>(...o: T) => new UnionSchema(o),
} as const;
The variance lesson is real and subtle: if refinements were typed Check<Output>, Output would appear in a contravariant position and Schema<string> would NOT be assignable to Schema<unknown> — breaking v.object and v.array. Type-erasing to Check<unknown> preserves covariance. And <const L> (02-10) is why v.literal("admin") infers "admin". Real library design is full of these decisions.

3. Using it — typed parse of untrusted data

usage.tstypescript 
import { v, type Infer } from "./src/index.js";

const User = v.object({
  id: v.number().int().positive(),
  name: v.string().min(1),
  email: v.string().email(),
  role: v.union(v.literal("admin"), v.literal("user")),
  bio: v.string().optional(),
});

type User = Infer<typeof User>;
// { id: number; name: string; email: string; role: "admin" | "user"; bio?: string }

// At the boundary, untrusted data becomes typed + validated in one step:
const result = User.safeParse(await fetch("/api/me").then((r) => r.json()));
if (result.success) {
  result.data.role; // "admin" | "user" — fully typed
} else {
  result.error.issues; // [{ path: ["email"], message: "Invalid email" }, ...]
}
This is the payoff of the entire part. One schema gives you validation AND types, errors aggregate with paths (02-06's recursion walks nested structures), literals stay narrow (02-10), and the result is a discriminated union (02-07) so you handle success/failure exhaustively. This is production-grade API-boundary safety.

Why two kinds of tests

Runtime tests (schemas.test.ts) prove validation works — rejecting bad data, aggregating issues, stripping unknown keys. Type-level tests (infer.test-d.ts, run with vitest --typecheck) prove the inference is correct using expectTypeOf(...).toEqualTypeOf(...) — the discipline from lesson 02-05. A validator must be correct at both levels, and now yours is provably so.
