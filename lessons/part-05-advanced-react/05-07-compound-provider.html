Component Patterns: Compound & Provider

🚀 Advanced ⏱️ ~30 min 🧩 API design

As components grow, how you design their API determines how pleasant they are to use. The compound component pattern (think <Tabs><Tab/></Tabs>) and the provider pattern give you flexible, expressive components that share state implicitly. These are the patterns behind every great component library — and exactly what interviewers probe for at senior level.

1. The compound component pattern

Tabs.tsxtsx 
import { createContext, useContext, useState, type ReactNode } from "react";

interface TabsContextValue { active: string; setActive: (id: string) => void; }
const TabsContext = createContext<TabsContextValue | null>(null);
const useTabs = () => {
  const ctx = useContext(TabsContext);
  if (!ctx) throw new Error("Tab parts must be used inside <Tabs>");
  return ctx;
};

function Tabs({ defaultTab, children }: { defaultTab: string; children: ReactNode }) {
  const [active, setActive] = useState(defaultTab);
  return <TabsContext value={{ active, setActive }}>{children}</TabsContext>;
}
function TabList({ children }: { children: ReactNode }) {
  return <div role="tablist">{children}</div>;
}
function Tab({ id, children }: { id: string; children: ReactNode }) {
  const { active, setActive } = useTabs();
  return (
    <button role="tab" aria-selected={active === id} onClick={() => setActive(id)}>
      {children}
    </button>
  );
}
function TabPanel({ id, children }: { id: string; children: ReactNode }) {
  const { active } = useTabs();
  return active === id ? <div role="tabpanel">{children}</div> : null;
}

// Attach the parts for a clean namespace:
Tabs.List = TabList; Tabs.Tab = Tab; Tabs.Panel = TabPanel;
export { Tabs };
Compound components share state implicitly through context, so the consumer composes freely without wiring props between parts. The parent (Tabs) owns the state; the children (Tab, TabPanel) read it via a private context + a guard hook. Attaching parts as Tabs.Tab gives a tidy, discoverable namespace.

2. The consumer's experience

usage.tsxtsx 
<Tabs defaultTab="profile">
  <Tabs.List>
    <Tabs.Tab id="profile">Profile</Tabs.Tab>
    <Tabs.Tab id="settings">Settings</Tabs.Tab>
  </Tabs.List>
  <Tabs.Panel id="profile">Your profile…</Tabs.Panel>
  <Tabs.Panel id="settings">Your settings…</Tabs.Panel>
</Tabs>
// Flexible: reorder, wrap, or style the parts however you like.
// No prop drilling — the parts coordinate through context internally.
Compare to a monolithic <Tabs tabs={[...]} /> with a giant config prop. The compound API reads like HTML, supports arbitrary markup between parts, and is far more flexible. This is exactly how Radix UI, Headless UI, and shadcn/ui design their primitives (Part 6).

3. The provider pattern

You've already built this in 04-09: a provider component owns state and exposes it via a typed custom hook, so any descendant can read/update it. It's the pattern for app-wide concerns — auth, theme, toasts, feature flags. The compound pattern is provider + a fixed set of child "parts".

⚡
Pro-tip · Other patterns you'll meet

Slots (named children props like header/footer), polymorphic components (an as prop to change the rendered element), and state reducers (letting consumers customise internal state transitions). All build on the typing skills from Parts 1–2. We use the headless variant next lesson.

🎓 Key takeaways

  • Compound components share state via context so parts compose freely (<Tabs><Tabs.Tab/>).
  • The parent owns state; child parts read it through a private context + a guard hook.
  • Attach parts as properties (Tabs.Tab) for a clean, discoverable namespace.
  • The provider pattern (04-09) shares app-wide state via a typed custom hook.
  • These patterns power Radix/Headless UI/shadcn — and signal senior-level component design.
