Reconciliation & How React Renders

🚀 Advanced ⏱️ ~30 min 🧠 Under the hood

To write fast, bug-free React, you need to understand what actually happens when a component renders. This lesson opens the engine: the render/commit phases, the Virtual DOM, the reconciliation (diffing) algorithm, and exactly why key matters so much. This mental model is what separates engineers who fight React from those who command it.

1. Render vs Commit

🧩
Concept · Two phases

Render phase: React calls your component functions to produce a tree of elements (the Virtual DOM). This must be pure — no side effects. Commit phase: React compares the new tree to the previous one and applies the minimal set of real DOM mutations. Effects (useEffect) run after commit. Rendering ≠ touching the DOM; it's computing what the DOM should be.

2. The Virtual DOM & reconciliation

Each render produces a lightweight JavaScript description of the UI (the elements from your JSX). React reconciles the new description against the previous one — a diffing algorithm — and updates only what changed. Direct DOM manipulation is slow; computing a diff in memory and batching minimal updates is fast.

render-trigger.tsxtsx 
// A component re-renders when:
//   1. its own state changes (setState)
//   2. its parent re-renders
//   3. a context it consumes changes
// On re-render, React re-runs the function, builds a new element tree,
// diffs it against the last one, and commits only the differences.

function Parent() {
  const [n, setN] = useState(0);
  return (
    <div>
      <button onClick={() => setN(n + 1)}>{n}</button>
      <Child />   {/* re-renders when Parent does — even though its props didn't change */}
    </div>
  );
}
// React.memo (04-10) or the React Compiler can skip Child's re-render
// when its props are unchanged.
Re-rendering is not re-mounting. When state changes, React re-runs the function and diffs — it does not destroy and rebuild the DOM. A child re-renders when its parent does, but if its output is identical, the commit phase changes nothing in the DOM. "Render" is cheap computation; "commit" is the expensive DOM work React minimises.

3. The diffing rules

  • Different element type → full replace. <div> becoming <section> means React tears down the old subtree and builds a new one (state is lost).
  • Same type → update props in place. React keeps the DOM node and just changes the attributes/children that differ.
  • Lists are matched by key. Keys tell React which item is which across renders, so it can reorder/insert/remove efficiently and preserve each item's state.

4. Why keys matter (the deep reason)

why-keys.tsxtsx 
// Each row has its own state (the input). With index keys, deleting the
// FIRST item shifts everyone's key up by one — React thinks item 0 just
// "changed text" rather than "was removed", so the input values end up on
// the WRONG rows. With stable item.id keys, React tracks identity correctly.

{rows.map((row, i) => (
  <input key={i} defaultValue={row.label} />        // ❌ bug on reorder/delete
))}

{rows.map((row) => (
  <input key={row.id} defaultValue={row.label} />   // ✅ identity preserved
))}

// You can also FORCE a remount by changing a key — handy to reset a
// component's state when an id changes:
<UserProfile key={userId} userId={userId} />
Keys are identity, not order. They tell reconciliation "this element is the same logical thing as before". Using the index breaks identity when the list changes. Bonus technique: deliberately changing a key forces React to remount a component (resetting its state) — the idiomatic alternative to a "reset on prop change" effect (04-07).
📝
Exercise · See reconciliation in action

Build a list of inputs with uncontrolled defaultValues, once with key={index} and once with key={item.id}. Type into them, then delete the first item. Observe how the index version scrambles the values and the id version doesn't. Then add <Profile key={id} /> and confirm changing the id resets its internal state.

🎓 Key takeaways

  • Rendering has two phases: render (pure, builds the element tree) and commit (minimal DOM updates).
  • The Virtual DOM + reconciliation diff trees in memory and apply only the changes.
  • Diffing: different type → replace subtree; same type → update in place; lists → matched by key.
  • Keys are identity, not order — use stable IDs; changing a key intentionally remounts (resets) a component.
  • Re-render ≠ re-mount ≠ DOM change — understanding this is the basis of all performance work.
