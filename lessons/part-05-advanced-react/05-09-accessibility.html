Accessibility (a11y) Done Right

🚀 Advanced · essential ⏱️ ~30 min ♿ For everyone

Accessibility means your app works for everyone — including people using screen readers, keyboard-only navigation, or other assistive technology. It's not optional: it's a legal requirement in many jurisdictions, a quality bar at every top company, and simply the right thing to do. The good news: most accessibility comes free from using the right HTML, and TypeScript helps you get the details right.

1. Semantic HTML is 80% of accessibility

semantic.tsxtsx 
// ❌ A div pretending to be a button — invisible to screen readers,
//    not keyboard-focusable, no Enter/Space handling:
<div className="button" onClick={handleClick}>Save</div>

// ✅ A real button — focusable, announced as a button, keyboard-activatable:
<button onClick={handleClick}>Save</button>

// Use elements for their MEANING, not their looks (style with CSS):
<nav>…</nav>  <main>…</main>  <header>…</header>  <footer>…</footer>
<button>  <a href>  <label htmlFor>  <ul>/<li>  <h1>…<h6> (in order)
The single biggest a11y win is using the right element. A real <button> is focusable, keyboard-operable, and announced correctly — for free. A clickable <div> breaks all of that and forces you to re-implement it badly. Reach for semantic elements first; add ARIA only when no semantic element fits.

2. Labels, forms, and focus

forms-a11y.tsxtsx 
import { useId } from "react";

function Field({ label }: { label: string }) {
  const id = useId();                 // stable unique id (05-08)
  const errorId = `${id}-error`;
  return (
    <div>
      <label htmlFor={id}>{label}</label>          {/* explicit association */}
      <input id={id} aria-describedby={errorId} aria-invalid={true} />
      <p id={errorId} role="alert">This field is required</p>
    </div>
  );
}
// Every input needs a real <label htmlFor>. Errors use role="alert" so
// screen readers announce them, and aria-describedby links them to the input.
Forms are where a11y matters most. Every input needs an associated <label> (use useId to link them). Announce errors with role="alert" and connect them via aria-describedby. Manage focus on route changes and when opening modals (move focus in, trap it, restore it on close — lesson 05-06).

3. Keyboard, contrast & ARIA

  • Keyboard: everything interactive must be reachable with Tab and operable with Enter/Space (and Escape to dismiss). Never remove focus outlines without a visible replacement.
  • Contrast: text must meet WCAG contrast ratios (4.5:1 for normal text). Don't convey meaning by colour alone (add icons/text).
  • ARIA, sparingly: ARIA attributes describe roles/states to assistive tech (aria-label, aria-expanded, aria-live). The first rule of ARIA: don't use ARIA if a native element does the job.
⚡
Pro-tip · Automate and audit

Add eslint-plugin-jsx-a11y (catches missing labels/alt text as you code), test with axe (e.g. jest-axe / Playwright's axe integration), and actually navigate your app with only the keyboard and a screen reader (VoiceOver/NVDA). Testing Library encourages a11y by querying via roles and labels (next lesson) — write accessible UIs and your tests get easier.

📝
Exercise · Make a widget accessible

Take a <div>-based "button" and dropdown and rebuild them accessibly: real <button>s, labelled inputs, keyboard support (Tab/Enter/Escape/arrow keys), aria-expanded, and visible focus states. Run eslint-plugin-jsx-a11y and navigate it with only the keyboard.

🎓 Key takeaways

  • Semantic HTML gives you most accessibility for free — use the right element, not a styled div.
  • Associate every input with a <label htmlFor>; announce errors with role="alert" + aria-describedby.
  • Ensure full keyboard operability, visible focus, and sufficient colour contrast.
  • Use ARIA sparingly — only when no native element fits.
  • Automate with eslint-plugin-jsx-a11y + axe, and test by hand with keyboard + screen reader.
