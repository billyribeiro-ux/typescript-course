Performance Profiling & Optimization

🚀 Advanced ⏱️ ~30 min ⚡ Make it fast

Performance work follows one rule: measure first, optimise second. Guessing wastes time and often makes code worse. This lesson covers the React DevTools Profiler, the common causes of slowness, and the concrete techniques — many now automated by the React Compiler — to fix them. You'll learn to diagnose, not guess.

1. Measure with the Profiler

📊
Concept · The React DevTools Profiler

Install React DevTools, open the Profiler tab, hit record, interact, stop. It shows a flame graph of which components rendered, how long each took, and why they rendered. This is your source of truth — always profile before changing anything. "It feels slow" is not a diagnosis.

2. The usual suspects

SymptomCauseFix
Everything re-renders on every keystrokeState too high in the treeMove state down / colocate it
Expensive list re-renders constantlyNew object/array/fn props each renderMemoize (or React Compiler)
Big list janks on scrollRendering thousands of DOM nodesVirtualization (windowing)
Slow initial loadHuge JS bundleCode splitting / lazy loading

3. Colocation & lifting state down

colocate.tsxtsx 
// ❌ Typing in the search box re-renders the ENTIRE expensive list:
function Page() {
  const [query, setQuery] = useState("");
  return (
    <>
      <input value={query} onChange={(e) => setQuery(e.target.value)} />
      <ExpensiveList />   {/* re-renders on every keystroke! */}
    </>
  );
}

// ✅ Push the state DOWN into the component that actually uses it:
function SearchBox() {
  const [query, setQuery] = useState("");
  return <input value={query} onChange={(e) => setQuery(e.target.value)} />;
}
function Page2() {
  return (<><SearchBox /><ExpensiveList /></>); // list no longer re-renders on typing
}
The cheapest optimization is structural. State only triggers re-renders of the component that owns it and its descendants. Keep state as low and as close to where it's used as possible ("colocation"). Often this removes a performance problem entirely — before you reach for any memoization.

4. Virtualization & code splitting

splitting.tsxtsx 
import { lazy, Suspense } from "react";

// Code splitting: only download the Editor's JS when it's actually shown.
const Editor = lazy(() => import("./Editor.js"));

function App({ showEditor }: { showEditor: boolean }) {
  return (
    <Suspense fallback={<p>Loading editor…</p>}>
      {showEditor && <Editor />}
    </Suspense>
  );
}

// Virtualization (windowing): render only the ~20 rows currently visible,
// not all 10,000. Use @tanstack/react-virtual (Part 6) for big lists/tables.
Two heavy-hitters for real apps: code splitting with lazy() + Suspense (next lesson) shrinks the initial bundle by loading routes/components on demand; virtualization renders only the visible portion of a huge list. Both attack the most common real-world slowdowns: big bundles and big lists.

Exercise · Diagnose then fix

Build a page with a search input and a list of 5,000 items that re-renders on each keystroke. Profile it. Then fix it by colocating the search state. Profile again and compare. Finally, lazy-load a heavy "details" panel and watch the initial bundle shrink in the Network tab.

🎓 Key takeaways

  • Measure first with the React DevTools Profiler — never optimise on a hunch.
  • The cheapest fix is structural: colocate state low so fewer components re-render.
  • Code splitting (lazy + Suspense) shrinks the initial bundle.
  • Virtualization renders only visible rows of huge lists.
  • The React Compiler automates micro-memoization; you focus on structure and measurement.
