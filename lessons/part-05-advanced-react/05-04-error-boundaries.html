Error Boundaries & Resilience

🚀 Advanced ⏱️ ~26 min 🛡️ Don't crash the app

Without protection, an error thrown during render unmounts your entire React tree — a blank white screen for the user. Error boundaries contain failures: they catch render errors in a subtree and show a fallback, keeping the rest of the app alive. Combined with Suspense, they give you a complete declarative model for loading and error states.

1. An error boundary

ErrorBoundary.tsxtsx 
import { Component, type ErrorInfo, type ReactNode } from "react";

interface Props { fallback: ReactNode; children: ReactNode; }
interface State { hasError: boolean; }

// Error boundaries must (still) be class components — one of the few cases:
export class ErrorBoundary extends Component<Props, State> {
  state: State = { hasError: false };

  static getDerivedStateFromError(): State {
    return { hasError: true };           // render the fallback next
  }
  componentDidCatch(error: Error, info: ErrorInfo) {
    // Report to your error-tracking service (Sentry, etc.) — Part 8:
    console.error("Caught by boundary:", error, info.componentStack);
  }
  render() {
    return this.state.hasError ? this.props.fallback : this.props.children;
  }
}
One of the rare places you still write a class. getDerivedStateFromError switches to the fallback; componentDidCatch is where you log to an error-tracking service. In real apps you'll use the react-error-boundary library (a function-component wrapper with reset support), but understanding the primitive matters.

2. Composing with Suspense

resilient.tsxtsx 
function Widget({ dataPromise }: { dataPromise: Promise<Data> }) {
  return (
    <ErrorBoundary fallback={<p role="alert">Couldn’t load this widget.</p>}>
      <Suspense fallback={<Skeleton />}>
        <Content dataPromise={dataPromise} />
      </Suspense>
    </ErrorBoundary>
  );
}
// Loading → Skeleton (Suspense). Failure → alert (ErrorBoundary).
// Success → Content. The three async states, declaratively, per region.
Error boundary + Suspense = complete async UI. Wrap each independent region so one widget's failure or slowness doesn't take down the page. This is the resilient, granular pattern used in production dashboards: every panel loads and fails independently.

3. What boundaries do and don't catch

Caught ✅NOT caught ❌
Errors during renderErrors in event handlers (use try/catch)
Errors in lifecycle/effects' render pathAsync errors outside React (use .catch)
Errors in constructors of childrenErrors in the boundary itself
⚠️
Gotcha · Event handler errors aren't caught

Boundaries only catch errors thrown during rendering. An error inside an onClick handler won't trigger them — handle those with a regular try/catch and your own state. Boundaries are for unexpected render-time crashes, not normal control flow.

📝
Exercise · Contain a crash

Build a <BuggyWidget /> that throws during render when a prop is invalid. Wrap two of them in separate ErrorBoundarys alongside a working widget. Trigger one crash and confirm only that widget shows its fallback while the rest of the page keeps working. Add a "Try again" reset button.

🎓 Key takeaways

  • Error boundaries catch render-time errors in a subtree and show a fallback — preventing whole-app crashes.
  • They're class components (getDerivedStateFromError + componentDidCatch); use react-error-boundary in practice.
  • Compose ErrorBoundary + Suspense per region for complete loading/error/success states.
  • They do not catch event-handler or async errors — use try/catch there.
  • componentDidCatch is where you report to error tracking (Part 8).
