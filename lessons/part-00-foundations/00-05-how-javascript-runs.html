How JavaScript Runs: Engines, Node & the Browser

🎯 Beginner ⏱️ ~22 min 🧠 Mental model

JavaScript is the only language that runs natively in every web browser — and, thanks to Node, on servers too. To write it well you need a clear picture of what runs your code, where it runs, and the single most important rule of how it executes. This is the model that will stop async code from ever confusing you later.

1. Engines: the thing that runs JavaScript

A JavaScript engine reads your code and executes it. The most famous is V8, built by Google — it powers Chrome and Node.js. Other engines include JavaScriptCore (Safari) and SpiderMonkey (Firefox). The engine parses your text, compiles it to fast machine code just-in-time, and runs it.

🧩
Concept · Two homes for JavaScript

The browser runs JS to make web pages interactive and gives it access to the page (the DOM), the network, and the screen. Node.js runs the same language on your computer or a server, and gives it access to files, databases, and the operating system. Same language, two sets of superpowers.

2. The call stack: one thing at a time

JavaScript is single-threaded: it does exactly one thing at a time, using a structure called the call stack. When you call a function, it's pushed onto the stack; when it returns, it's popped off. Read this and predict the output before revealing it:

stack.jsjavascript 
function greet(name) {
  return "Hello, " + name;
}

function welcome() {
  const message = greet("Ada");   // greet is pushed, runs, returns, pops
  console.log(message);
}

welcome(); // -> "Hello, Ada"
What's happening: calling welcome() pushes it onto the stack. Inside, it calls greet("Ada"), which pushes on top, runs, returns its string, and pops off. Then console.log runs. The stack is strictly last-in, first-out.

3. The event loop (the 60-second version)

If JS only does one thing at a time, how does it handle a network request that takes two seconds without freezing? The answer is the event loop. Slow operations (timers, network, file reads) are handed off to the environment (browser or Node) to do in the background. When they finish, their follow-up code is queued and run when the stack is free.

eventloop.jsjavascript 
console.log("1 — first");

setTimeout(() => {
  console.log("3 — later (after the stack clears)");
}, 0);

console.log("2 — second");

// Output order: 1, 2, 3  — even though the timeout is 0ms!
The lesson: setTimeout doesn't run immediately even at 0ms. It's queued and runs only after the current synchronous code finishes. This single idea explains almost all "why did this run in that order?!" surprises. We'll go deep on async in Lesson 11.
✨
2026 context · Node, Deno & Bun

Node is the established standard, but you'll hear about Deno and Bun — newer runtimes that also run JS/TS with modern features built in. This course uses Node 24 because it's the safest, most universal choice, but the language you're learning runs on all of them.

Exercise · Predict, then verify

Add a second setTimeout with a 10ms delay and another console.log at the very end. Write down the order you expect, then run it with node eventloop.js. Did reality match your model? Adjust your model, not the result.

🎓 Key takeaways

  • A JS engine (like V8) runs your code; it powers both Chrome and Node.
  • JS is single-threaded and uses a call stack — one thing at a time, last-in first-out.
  • Slow work is offloaded; the event loop runs the follow-up later, once the stack is free.
  • setTimeout(fn, 0) still runs after the current code — async ≠ immediate.
  • Browser and Node share the language but expose different capabilities.
